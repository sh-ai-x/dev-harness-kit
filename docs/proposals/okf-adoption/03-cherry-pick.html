왜 이 1건만 통과했는가

9개 요소 중 8개는 dev-kit에 이미 대응 표면이 있거나(R1–R3, D2), 저장소 결정과 충돌하거나(R4), 저장소 정책을 스펙이 표현하지 못하거나(R5), 없는 인프라를 전제한다(R6). sources(D1)는 유용하지만 스펙이 두 달 만에 옮긴 필드다.

stale_after 하나만 다른 이유는 dev-kit에 대응 표면이 있는데 그것이 비결정론적 이라는 점이다.

층현재성질
staleness 탐지rg 검색 + git log 판단 (SKILL.md:48–49)LLM 추정, 호출해야 작동
만료 신호없음—

stale_after는 두 번째 칸을 채운다. 채워지면 첫 번째 칸의 휴리스틱 산문을 지울 수 있으므로, 추가가 곧 제거를 만든다 — thin-harness 게이트를 통과하는 유일한 구조다. 나머지 8건에는 이 성질이 없다.

delta 회계 (thin-harness 게이트)

MEMORY thin-harness discipline: 채택 건당 prompt-token delta ≤ 0. 바이트 실측으로 검증한다.

status: 필드추가0 (§5.4 기본값 stable 활용, 미기재)

보수적으로 대체 1줄을 90 B로 잡아도 −138 B. 대체 문장을 생략하면 −228 B. 어느 쪽이든 게이트 통과.

왜 tools/check_doc_lifecycle.py 와 테스트 바이트는 계산에서 빠지는가

thin-harness 게이트의 단위는 prompt-token이다. tools/*.py와 tests/*.py는 어떤 프롬프트에도 로드되지 않는다 — 모델이 읽는 것은 스킬 프롬프트와 규칙 문서이고, 체커는 CI에서 subprocess로 실행된다. 저장소 총 바이트는 늘지만 프롬프트 토큰은 줄어든다. 이 해석에 이견이 있으면 리뷰에서 반박해 달라 — 게이트 통과 여부가 이 한 줄에 달려 있다.

검증 명령:

sed -n '48,49p' skills/docs-maintenance/SKILL.md | wc -c   # → 358
printf 'stale_after: 2026-11-30\n' | wc -c                 # → 26

게이트 배선

.github/workflows/ci.yml 의 validate 잡에 스텝 1개를 추가한다. 이 잡은 이미 plugin manifest 검증 · skill count · version freshness · bash 훅 문법 · python import를 순차 실행하므로, 문서 lifecycle 검사도 같은 성격이다.

- name: Doc lifecycle (stale_after)
  run: python3 tools/check_doc_lifecycle.py

체커 계약:

입력동작

stale_after < today파일명 + 만료일 stderr 출력, exit 1

frontmatter 파싱 실패exit 1 (fail-closed — 규칙 문서의 frontmatter는 이미 파싱 가능해야 함)

파서는 tools/harness_audit.py:81 의 yaml.safe_load 패턴을 재사용한다. 신규 의존성 없음 (requirements.lock 에 PyYAML 존재).

Limitations

  • 게이트는 만료를 보고할 뿐 문서를 갱신하지 않는다. 갱신은 사람 또는 /dev-kit:docs-maintenance 호출
