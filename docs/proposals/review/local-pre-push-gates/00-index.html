One-paragraph summary

PR #829 was merged with GitHub issue sync check failing because the PR body referenced three closed issues (#726, #397, #625) alongside the one it closed (#823). The gate is deterministic (Python parser + gh api) and ran on GH Actions only — so the developer had no signal until after push. This proposal migrates every deterministic gate to a local pre-push hook (Tier A), leaves LLM-judge gates remote-only (Tier B), and reserves post-merge automation as Tier C. Net: failures surface in <10s on the developer's workstation, no more "rerun CI until green."

Why now (triggering evidence)

Three converging signals:

  1. PR #829 merged with a red gate (run #102301168018, 2026-09-09). The merge queue did not block on issue-sync, but the failure is still in gh pr checks output. The author had no local signal during development.
  1. The user's repeated pattern: "local에서 실패시에 계속 돌려야한 문제가 있는게 반복적으로 돌릴 필요 없이" — the user has explicitly asked for a pre-push mirror of GH-Actions gates that is fast enough to run on every push.
  1. The gate surface has grown: 11 workflows (was 8 in 2026-08), 6 of them LLM-judge gates. The marginal cost of running pytest tests/ + ruff + issue_sync on every push is <10s; running LLM judges is 1-3 min per push and is the user-visible "rerun until green" pain.

What this proposal is NOT

  • Not a removal of any remote GH Actions gate. The remote stays as the authoritative source of truth (PR branch protection cannot be enforced locally).
  • Not a replacement for LLM judges. Tier B gates stay remote-only because they need provider API keys and 1-3 min of judge time — too expensive to run per-push.
  • Not a CI runtime optimizer. Tier A gates don't reduce GH Actions minutes; they only reduce the rate of red pushes. The two metrics are decoupled.
