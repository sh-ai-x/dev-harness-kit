# Maintenance gate — registry-index sub-gate

The `/dev-kit:maintenance` gate enforces two independent docs-coverage
rules on every PR:

1. **Path-level docs check** (existing). When the PR touches a
   production path under `bin/` / `commands/` / `lib/` / `tools/` /
   `hooks/` / `skills/` / `.githooks/` / `.claude/` / `.codex/` /
   `.github/`, it must also touch a `docs/*` file (excluding
   `docs/stages/STAGES.md` and `docs/repo/REPOSITORY-MAP.md`, which
   are auto-managed), or carry the `docs-not-required:` marker in
   the PR body.

2. **Skill/command registry check** (added 2026-09, PR #802; root
   README made mandatory 2026-09, PR #803). When the PR adds a NEW
   (`changeType=ADDED`) `skills/<name>/SKILL.md` or
   new `skills/<name>/SKILL.md`, it MUST also touch the **root `README.md`**:

   | Doc | Status |
   |---|---|
   | `README.md` (top level) | **MANDATORY** — the check passes on this file alone |
   | `docs/skills/README.md` (English) | good practice, not a substitute |
   | `docs/skills/README.ko.md` (Korean) | good practice, not a substitute |
   | n/a (commands/ removed) | n/a |
   | `skills/README.md` | never counts — auto-generated |

   OR carry the `docs-not-required:` marker.

   ### Why the root README is mandatory

   The rule used to accept any one of the four manually maintained
   registry docs. That made the gate satisfiable without the root README
   ever learning the skill existed — which is exactly what happened:

   - `/dev-kit:gate-select` (#786) touched only `docs/skills/README.md`.
     The gate passed. The root README had zero mentions of the skill,
     and `docs/skills/README.md`'s own row admitted "consumer docs land
     in a follow-up PR" that never came.
   - `guard-mode` (#787), `worktree-prune` (#788), and `harness-mode`
     reached `main` the same way.

   The root README is the front door: operators who read it and nothing
   else must still see every skill they can type. A secondary index is
   where they go for detail, not for discovery.

   The auto-generated `skills/README.md` (regenerated by
   `tools/build_skills_readme.py`) is excluded from every tier —
   counting it would make the gate a near-no-op (operators just run the
   regen tool).

   ### Path-level check vs. content check

   The deterministic gate can only see *that* `README.md` is in the
   change set, not *what* changed in it. Two layers close that gap:

   - `tests/test_readme_skill_registry.py` asserts every skill with
     `user-invocable: true` is named in the root README as
     `/dev-kit:<name>`. This is the real content invariant, and it fails
     the test suite (not just the PR gate) when a skill goes
     unregistered.
   - The LLM-judge prompts in `.github/workflows/maintenance.yml` ask
     the judge to confirm the README edit actually registers the skill
     rather than touching the file incidentally.

### Implementation

- `lib/maintenance_gate.py::parse_file_entry` accepts both legacy
  bare paths (`"lib/foo.py"`, status defaults to `modified`) and
  the new file-status-aware form (`"lib/foo.py:added"`). Status is
  lowercased so GitHub's uppercase `changeType` values
  (ADDED/MODIFIED/DELETED/RENAMED/COPIED) match the lowercase
  frozenset.
- `lib/maintenance_gate.py::registry_index_updated_ok` is the pure
  function. `docs_updated_ok` delegates to it whenever the diff has a
  new skill/command, so the two entry points cannot drift; the registry
  failure surfaces ahead of the generic path-level one (more
  actionable).
- `_PRIMARY_REGISTRY_DOC` (`"README.md"`) is the mandatory doc;
  `_SECONDARY_REGISTRY_DOCS` are named in the failure message so an
  operator who updated `docs/skills/README.md` is told their work
  counted for something but does not exempt them.
- `.github/workflows/maintenance.yml` extracts `<changeType>\t<path>`
  per file via `gh pr view --json files --jq '.files[] |
  [.changeType, .path] | @tsv'`. The bash loop reads
  `IFS=$'\t' read -r status path` and passes
  `"${path}:${status}"` to `--changed-files`.
- `bin/review-local.sh` exposes `files_with_status` so a future
  local `--docs-check` parity PR can use it.

### Edge cases

- **Renames** (`changeType=RENAMED`) do NOT trigger the registry
  check. GitHub's similarity threshold makes `renamed` inconsistent
  across equivalent PRs (typo-fix rename → still points to the
  same path in `skills/README.md`).
- **Modified existing skills/commands** do NOT trigger the check.
  Only NEW files do.
- **Malformed `--changed-files` entries** (multi-colon, empty path,
  empty status) are rejected by `parse_file_entry` with
  `ValueError`. The CLI wraps both `docs_updated_ok` and
  `registry_index_updated_ok` in `try/except ValueError` so a
  malformed entry emits a clean
  `{"docs_ok": false, "reason": "malformed changed-files entry: ..."}`
  JSON line (fail-closed, but actionable).

### Tests

- `tests/test_readme_skill_registry.py` — the content invariant: every
  `user-invocable: true` skill is named in the root README, and the
  README's bootstrap-prompt claim matches `skills/bootstrap/SKILL.md`
- `tests/test_maintenance_gate.py::TestRegistryIndexCheck` — the
  primary/secondary split, including a nested-`README.md` case that
  guards against an `endswith()` implementation
- `tests/test_maintenance_gate.py::TestParseFileEntry` — `path:status`
  parsing and malformed-entry rejection
- `tests/test_maintenance_gate.py::TestRegistryOnlyCLI` and
  `TestCLISubprocess` — the same logic through the CLI the workflow
  shells out to, `path:status` and malformed entries included
- `tests/test_review_yml_touch_probe.py::TestMaintenanceGateFileStatusExtraction`
  pins the jq + bash + review-local projection across three copies

Run `python3 -m pytest tests/test_maintenance_gate.py
tests/test_readme_skill_registry.py -q` for the current counts rather
than trusting a number written here.
