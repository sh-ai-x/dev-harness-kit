Decision rule

For each gate, ask three questions in order:

  1. Is it deterministic? (Same input → same output.) If no → Tier B (remote) or Tier C (post-merge).
  2. Does it need network state that the developer doesn't have? (e.g. gh api for issue states, Linear API, provider LLM key.) If yes → Tier B.
  3. Does it take >5s to complete locally? If yes → Tier B (pre-push hook would make pushes feel slow).

A gate is Tier A iff all three answers are: deterministic, no-network-required, <5s.

A gate is Tier C iff it is triggered by a merge event (e.g. version-bump.yml).

Everything else is Tier B (remote-only).

Total deterministic wall-clock: ~30-90s on a clean tree, <10s on warm pytest cache. Acceptable for a git push.

The `gh api` call in issue-sync is optional:

  • With --offline: parser emits the ref list and warns (does not fail). Developer runs the full check on push if they want the fail-fast signal.
  • Without --offline (default): runs the same gh api check as the workflow. The developer needs gh auth status green.
  • Alternative: use gh pr view --json body,title after git push to fill in the missing metadata. Documented in 03-implementation.yaml.

Why this is NOT a CI runtime optimizer

The proposal does not reduce GH Actions minutes. It only reduces the rate of red pushes. A developer who fixes a failing gate locally still pushes the green version to GH Actions, which then runs the same Tier-A gates (plus Tier B).

The only GH Actions savings are:

  1. Pushes blocked at pre-push never reach pull_request events.
  2. Fewer rerun calls on already-red workflows.

Both are second-order effects. The primary metric is developer time-to-fix, not GH Actions spend.

What this is NOT

  • Not a wholesale CI migration. No remote gate is removed.
  • Not a substitute for LLM judges. Tier B stays remote.
  • Not a CI runtime cost reduction. See above.
  • Not a magic bullet for fork-PRs. fork-pr-review.yml is a different problem (GitHub security model — fork PRs can't access secrets) and stays as-is.
