Problem statement

Bug mechanism

Three independent functions disagree on skill naming convention:

LayerFunctionEmitsExample
Catalog discovery_discover_catalog_skills (skill_usage_render.py:153)dev-kit:<name>dev-kit:worktree-prune
Telemetry normalization_normalize_usage_record (skill_usage_normalize.py)bare nameworktree-prune
Candidate filter_run_propose_delete (skill_usage_render.py:186-189)catalog namedev-kit:worktree-prune

Patch (tools/skill_usage_render.py)

Replace the catalog seeding loop in _run_propose_delete (lines 181-184):

# BEFORE
seeded = dict(skills)
for name in _discover_catalog_skills(repo_root):
    seeded.setdefault(name, {"turns": 0, "invocations": 0,
                             "last_seen": None})

With prefix-aware seeding that merges prefixed + bare telemetry rows:

# AFTER
seeded = dict(skills)
for name in _discover_catalog_skills(repo_root):
    # Telemetry captures skills under their bare name (e.g. "worktree-prune"),
    # not the prefixed form ("dev-kit:worktree-prune"). Merge both rows so a
    # skill with bare-name usage isn't flagged as 0/0. last_seen is the max.
    bare = name.split(":", 1)[-1] if ":" in name else name
    merged = {"turns": 0, "invocations": 0, "last_seen": None}
    for src in (skills.get(name), skills.get(bare)):
        if not src:
            continue
        merged["turns"] += src.get("turns", 0)
        merged["invocations"] += src.get("invocations", 0)
        ls = src.get("last_seen")
        if ls and (merged["last_seen"] is None or ls > merged["last_seen"]):
            merged["last_seen"] = ls
    seeded[name] = merged

Before / After

Before (current state)

tools/skill_usage_render.py::_run_propose_delete seeds prune candidates from the on-disk catalog under dev-kit:<name>, but _normalize_usage_record captures telemetry under the bare skill name. The 0/0 filter compares different names, so every user-invocable skill is flagged as unused regardless of actual dispatch volume.

Evidence

  • tools/skill_usage_render.py:153 — catalog emits prefixed dev-kit:<name>
  • tools/skill_usage_normalize.py — telemetry emits bare <name>
  • python3 tools/skill_usage.py --days 30 --propose-delete --dry-run reports 24 candidates today; 23 of them have heavy bare-name telemetry (babysit-pr-local 1988 turns, docs-maintenance 1794, review 1514, worktree-prune 838, security 560, linear 536, ...).

After (proposed state)

_run_propose_delete merges prefixed + bare telemetry rows when seeding from the catalog. A skill is "unused" iff BOTH the prefixed and the bare form have zero turns AND zero invocations within the window. Telemetry normalization is unchanged.

Files

  • tools/skill_usage_render.py

    Replace the 4-line catalog seeding loop with a prefix-aware merge that combines prefixed (dev-kit:<x>) and bare (<x>) telemetry rows. ~14 lines.

  • tests/test_skill_usage.py

    Add test_propose_delete_skips_bare_name_skills regression test that confirms a skill with bare-name telemetry is not flagged as a candidate. ~35 lines.

Pros

  • Surgical: only the seeding boundary changes; aggregate_skill_usage / _normalize_usage_record / format_table / filter_by_cwd_prefix are untouched
  • Telemetry semantics preserved — bare name remains source of truth, only the merge check is added
  • Test surface already imports the helpers; regression test uses them as fixtures without mocking
  • Fixes a real safety bug: prune-propose is currently unsafe to run because every skill is a candidate
  • Smallest possible diff: +14 / -4 in production code, +35 in tests

Cons

  • Naming convention is now implicit in two places (catalog discovery + new merge). A future telemetry refactor could re-introduce the drift.
  • A fresh checkout with no logs returns 0 candidates (was 24). This is the correct behavior, but operators used to the old output may notice.

Limitations

  • Cannot catch bare-name collisions across plugins (telemetry already scopes by cwd, so collisions are unlikely in practice)
  • Cannot detect future naming convention drift — the regression test pins the convention but does not auto-verify ongoing telemetry writes
  • Does not change the AskUserQuestion loop itself; once candidates are correctly filtered, the per-skill delete decision is unchanged
