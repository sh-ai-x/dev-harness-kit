Pattern 1 — LoopDetectionMiddleware (re-scored)

v0.3.194 verdict: APPLY (+4)

In v0.3.199, stage-gate.sh (NEW) already gates every stateful hook by reading .dev-kit/.active-hooks.json before the hook runs. This is not the same thing as doom-loop detection — it gates hook execution, not hook outcome. Doom-loop detection (3 identical calls in a row) is still a gap.

However, the gap is now smaller because:

  • The bash-guard, secret-scan, slop-detector, stop-verify, and tdd-guard all now source stage-gate.sh; a stage mismatch short-circuits before the loop-prone code runs.
  • The tdd-guard records the RED/GREEN boundary into .dev-kit/.tdd-cycle.json; a retry-loop in TDD now produces evidence that the system can flag.

Updated pros (4, was 5)

  1. Catches silent doom loops that would otherwise burn 5–10k tokens before timing out.
  2. Preserves the user's hourly $ budget — doom loops are the #1 silent cost driver.
  3. Additive only — adds a new hook, no existing behavior changes.
  4. Easy to test — fixture with 3 identical Bash calls triggers the warning; deterministic.

Updated cons (3, was 2)

  1. False positives on legitimate retries — same as before.
  2. Stage-gate already provides partial coverage — the new value-add is smaller than at v0.3.194 (the easy wins are taken).
  3. One more hook to maintain — hook count goes 16 → 17.

NEW Pattern 6 — PreCompletionChecklistMiddleware

Why now

LangChain reports 52.8% → 66.5% on Terminal Bench 2.0 with just a PreCompletionChecklistMiddleware — a small piece of middleware that forces the agent to verify against a checklist before declaring done [src:https://blog.langchain.com/improving-deep-agents-with-harness-engineering/;ts:2026-08-04;type:primary].

v0.3.199 state

No equivalent. The stop-verify.sh hook verifies build (lint, test, type) but not intent (does the change accomplish the user's stated goal, are the docs updated, are edge cases covered). The build passes but the user reads the diff and says "you didn't do what I asked."

Proposed implementation

Add a new module lib/pre_completion_checklist.py that reads:

  • The user's original request (from .dev-kit/hand-off/).
  • The diff (git diff HEAD~1).
  • The implementation file paths.

Then enforces a checklist before stop-verify.sh allows the agent to declare done:

□ Are the user's stated requirements addressed?
□ Are docs updated if behavior changed?
□ Are edge cases flagged in the diff?
□ Are public APIs documented?
□ Did the agent skip any tests marked as required?

Pros (4)

  1. Catches "build passes but wrong work" — the most common dev-harness-kit failure mode anecdotally.
  2. Composes with stop-verify — stop-verify is the build check; the new middleware is the intent check.
  3. Reuses the existing diff-extraction machinery in lib/.
  4. Doesn't require LLM-as-judge — the checklist is deterministic (or rule-based) for 80% of items.

Cons (3)

  1. New module to maintain — adds surface area.
  2. The "intent" check is fuzzy — needs careful prompt or rule design.
  3. One more failure mode — false positives on the intent check.

NEW Pattern 7 — CrashSignal in eval aggregates

Why now

Anthropic's langchain study reports: "a thrown scorer exception used to yield value=1, arithmetically identical to a legitimate lowest score; aggregate.compute() read only .value, so eval verdicts silently absorbed infrastructure failures as real signal."

v0.3.199 state

FIXED in #557. lib/behavior_scorers now exposes a crashed: bool on DimensionScore and routes crashed dims to ESCALATED, excluding them from the weighted-mean divisor.

Verdict: APPLIED (no work)

Open questions

  1. Phase ordering: should PreCompletionChecklist land before Long-running templates? The templates affect session-start; the checklist affects session-end. They're independent. Recommend parallel.
  2. Checklist medium: should the PreCompletionChecklist be a hook (mandatory) or a skill (advisory)? Mandate breaks existing flows; advisory is ignored. Recommend hook with a "skip with justification" escape.
  3. Doom-loop threshold: with stage-gate in place, is the 3-call threshold still right? Or 5? Recommend defer to first failure data after stage-gate is in production.
