Decision and scope

Adopt this as a two-phase cleanup. Phase 1 changes guard activation and removes the session-monitor feature. Phase 2 removes only skills, docs, and tests that meet the deletion rubric below. The implementation must not weaken catastrophic command blocking, secret scanning, prompt injection scanning, review/security checks, or completion verification.

The proposal is intentionally about policy and surface area. It does not add a replacement dashboard, background monitor, MCP layer, or a new model orchestration protocol.

Guard policy and scope precedence

Add one setting: DEV_KIT_GUARDS=on|off.

Resolution order is:

shell DEV_KIT_GUARDS
  > .claude/settings.local.json env.DEV_KIT_GUARDS
  > .claude/settings.json env.DEV_KIT_GUARDS
  > default: off

User-scope settings are not read for this key. They may enable the plugin so commands resolve, but they cannot activate repository guards. Invalid values are ignored with one compact diagnostic and resolve to the next layer. Plugin installation never writes this key. On the first /dev-kit:bootstrap, ask once:

Enable worktree, git, and TDD guards for this repo? [y/N]
If yes, save it to project scope or local scope? [project/local]

N leaves the effective default off. Y + project writes DEV_KIT_GUARDS=on to .claude/settings.json; Y + local writes it to .claude/settings.local.json. Existing settings are not silently overwritten. Re-running bootstrap reports the current value and keeps SessionStart prompt-free.

on enables worktree, git, and tdd guards in every session. off disables those three session-policy checks. Existing catastrophic and ask-tier hooks keep their own contracts and are not silently disabled by this setting.

SessionStart records policy only

session-start-check.sh classifies the checkout before emitting its context. The state writer records policy, policy_source, branch_class, and the effective guard map in .dev-kit/guard-mode.session.json.

With no explicit project/local/shell policy, every checkout resolves to off:

Checkoutworktree guardgit guardtdd guardreason
mainoffoffoffbootstrap-only choice; SessionStart stays prompt-free
feature worktreeoffoffoffdefault thin session
detached/outside projectoffoffoffno repository policy

An explicit DEV_KIT_GUARDS=on changes every row to on. An explicit off keeps every row off. The one-line SessionStart context reports the resolved policy and branch class. The hook never asks a question or blocks SessionStart; it writes the decision and leaves enforcement to the individual PreToolUse hooks. Bootstrap owns the one-time setup question and the project/local write.

Deletion rubric and candidates

A surface is removable only when all four checks pass:

  1. no runtime/import/manifest consumer remains;
  2. its behavior is either duplicated by a deterministic hook or has no current product value;
  3. a replacement command/path is documented when users need continuity;
  4. focused tests prove the absence or the retained contract.

First-wave deletion: the session-monitor code, its fixtures, tests, screenshot, ownership entry, and observability/workflow references. The eval-session judge remains; only the monitor handshake assertions are removed or rewritten.

Second-wave candidate: model-only build-tdd, build-verify, and build-refactor skills. Their deterministic enforcement already lives in hooks and their parent stages. Candidate-only, pending the usage and import scan: valuate, interview, learn, status, and prune-propose must not be deleted just because their prose is long; each needs a separate evidence-backed decision because it owns a distinct artifact or operator workflow.

Context and token budget

Active SKILL.md files should contain only: trigger, inputs, outputs, state transition, hard invariant, and next hand-off. Detailed rationale belongs in the linked SSOT docs and proposal, not in every skill.

Measure before and after with the existing token analyzer and a stable file list. Acceptance target: at least 20% fewer instruction tokens in active skill files plus zero loss of command names, required files, hook names, or verification commands. Hook output is capped at one compact SessionStart context line; verbose diagnostics remain on disk or behind explicit status commands.

  1. Add the resolver/state truth table and bootstrap prompt tests first; the no-prompt SessionStart and all-off default are part of the contract.
  2. Wire the policy into worktree/git/tdd guards; run their focused hook suites.
  3. Remove session-monitor files and references; run import, README, documentation, and eval-session tests.
  4. Run the skill usage/import scan, delete only approved duplicate skills, and regenerate both skill indexes.

Required checks include pytest tests/test_guard_policy.py, the guard hook suites, a repository-wide git grep proving no live session_monitor reference remains, the skill registry audit, and a token analyzer report with the before/after file set.

Proposal lifecycle updates

Existing proposal records should be updated only when their design is demonstrably shipped. In particular, an implemented skill or hook must move from reviewing/ or pending/ to applied/ with started and shipped dates and a short modifications block when the code differs from the design. Removing a feature also updates its proposal to superseded or applied-with-changes; leaving stale draft text that describes shipped behavior is not acceptable.

The user accepted the thin default. The implementation is applied with the deletions and documentation substitutions recorded in modifications; only a main-branch-specific default or recurring SessionStart question remains deferred.

Before / After

Before (current state)

Plugin loading and guard activation are coupled too loosely. A user-scope plugin can be present before a project has made a guard decision, while SessionStart resets the session guard file to on. The current resolver has mode precedence but no equivalent project/local guard policy, and git-guard has no session policy check. The repository also ships a standalone session-monitor surface and several model-only skills whose rules duplicate deterministic hooks or the parent stage skills.

Evidence

  • hooks/lib/mode-resolve.sh:8-13,78-142 resolves shell/project/local mode but has no guard-policy layer and defaults an enabled project to full.
  • hooks/session-start-guard-mode-reset.sh:4-17 resets the session guards at every SessionStart; lib/guard_mode_state.py:54-63 defaults tdd/worktree to on.
  • hooks/worktree-guard.sh:46-49 and hooks/tdd-guard.sh:10-11 already contain deterministic enforcement; hooks/git-guard.sh:1-8 has no equivalent session-policy read.
  • hooks/session-start-check.sh:123-128 emits a main-checkout reminder but does not record an explicit on/off decision for the guards.
  • tools/session_monitor.py plus six split helpers, fixtures, tests/test_session_monitor.py, and two observability docs form a standalone cross-terminal session picker.
  • skills/build-tdd, skills/build-verify, and skills/build-refactor are model-only sub-skills while tdd-guard, stop-verify, prune, and the parent build/refactor skills carry the executable contracts.

After (proposed state)

Separate plugin discovery from guard activation. A compact project/local setting controls guards; user-scope plugin installation never enables repository safety policy by itself. SessionStart resolves the policy, detects main versus worktree, writes the effective decision to the session state, and emits one short context line. The default is off for every checkout, including main. SessionStart does not ask guard-by-guard questions and does not auto-enable a main-branch exception. During the first /dev-kit:bootstrap, the operator is asked once whether guards should be enabled and whether the choice belongs to shared project scope or this checkout's local scope.

Remove session-monitor and other proven-dead or duplicate surfaces, then trim surviving skill prose to invocation, inputs/outputs, invariants, and links to the SSOT. Keep deterministic safety, secret, injection, verification, review, and security hooks.

Pros

  • A user-scope plugin can be installed without silently imposing repository-specific edit or branch policy on every project.
  • Every unconfigured checkout starts with the same thin, predictable guard state instead of a hidden main-branch exception.
  • SessionStart records the effective decision, making on/off behavior inspectable and reproducible instead of implicit.
  • Deleting the session monitor and duplicate model-only layers reduces install surface, prompt tokens, tests, and documentation drift.
  • The retained safety and verification behavior remains deterministic and testable at the hook layer.

Cons

  • Guards stay off until bootstrap receives an explicit choice, so an unconfigured main checkout is intentionally permissive.
  • Bootstrap adds one setup decision; keeping it to enable/disable plus project/local scope avoids recurring session friction.

Limitations

  • This changes repository guard activation, not plugin discovery; user-scope installation may load the plugin but cannot turn guards on.
  • A later proposal may add a main-branch-specific default or prompt; this proposal deliberately keeps one explicit bootstrap choice.
