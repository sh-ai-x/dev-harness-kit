권고안 — 중복 작업을 줄이고 필수 검증은 유지

선택 재시도 + 검증 후 push + 준비 완료 시 최신화를 적용한다. strict=false 전환, 임의 verdict cache, 승인 우회는 구현 범위에 넣지 않는다.

상황제안 동작유지하는 보장
같은 입력의 확인된 runner/API 일시 장애실패 job과 필요한 downstream만 재시도성공한 독립 결과만 유지
실제 finding 수정같은 논리적 수정의 로컬 검증을 마친 뒤 push새 SHA에 정상 required gates
main 전진, 다른 blocker 미해결수정을 마치며 최신화 요청 중복 억제strict가 merge 차단
다른 blocker 해결, branch 뒤처짐최신 head/base로 최신화 요청 1건최신화 후 필수 gate 재실행
최신화 후 main 재전진새 base에 대해 다시 판단·최신화·검증stale 상태로 merge하지 않음

두 문제 모두에서 불필요한 반복은 줄인다. 다만 두 번째 문제의 필수 재검증 자체를 없애지는 않는다. 최신 main과의 통합 보장을 유지하면서 conflict 없음만으로 통과시킬 수는 없다.

1단계 — 같은 입력의 일시 실패에만 native retry

일시 장애 allowlist는 명확한 runner 인프라 장애, rate-limit 또는 일시적 provider/API 오류다. 테스트 assertion, lint/type 오류, 실제 review finding, 정책 차단은 수정 경로로 분류한다. 원인 불명, 안전성 관련 실패는 자동 재시도하지 않고 recovery 상태와 근거를 남긴다. 단순 failure/timeout 상태만으로 일시 장애라고 판정하지 않는다.

  • 한 job 장애: gh run rerun RUN_ID --job JOB_DATABASE_ID.
  • 여러 확인된 일시 장애: gh run rerun RUN_ID --failed. 같은 run에 결정적 실패가 섞이면 이 명령 대신 해당 transient job만 지정한다.
  • Actions jobs API에서 run ID와 job database ID를 구분해 조회한다. check-run ID를 run ID로 간주하지 않는다.
  • repository/PR/event/run_id/run_attempt/job_id, 원래 SHA/ref 및 관찰한 head/base, 실패 원인과 pending action을 저장한다. 실행 직전 fresh snapshot이 다르면 계획을 폐기하고 다시 분류한다.
  • 동일 원인·원본 run/head의 자동 retry 한도는 2회다. run_attempt 증가나 worker restart로 한도가 초기화되지 않는다. 같은 attempt의 중복 실행도 차단한다.
  • timeout·API 응답 유실로 재실행 접수가 불명확하면 먼저 GitHub attempt 상태를 재조회한다. 접수 여부를 모른 채 같은 mutation을 반복하지 않는다.

GitHub rerun은 원래 SHA/ref를 사용한다. 그래도 live PR body·댓글·설정을 다시 읽는 job은 입력이 달라질 수 있다. metadata 보완 후 gate-only 재실행은 그 gate가 실제 fresh evidence를 읽고 upstream 판단 입력이 영향을 받지 않았음이 확인된 경우에만 허용한다. 새 코드 수정으로 실패를 고친 경우에는 새 SHA 검증을 수행한다.

실제 run 34214518114에서는 review/security job이 success여도 Combined verdict gate는 실패했다. job 실행 성공은 verdict 승인과 다르다. 부정 verdict를 gate retry로 해결하거나 LLM을 통과할 때까지 다시 실행하지 않는다. 성공한 upstream output과 downstream gate의 부분 재실행 연결은 staging에서 확인하고 누락 결과를 성공으로 간주하지 않는다. 동일 head와 failure conclusion이라도 run_attempt/job 실행이 새로 생기면 fresh 로그를 읽고 다시 분류한다. 현재 이름·결론 중심 check-state cache만으로 이전 진단을 재사용하지 않는다. retry 식별자에는 workflow/run/job/attempt가 포함된다.

2단계 — 수정과 최신화 실행 시점 정리

기존 step 8도 로컬 검증 실패 시 push를 막는다. 추가 개선은 동일 root cause가 여러 check에 드러난 경우 알려진 관련 실패를 함께 해결하고 확인하는 것이다. 같은 논리적 수정을 로컬에서 완료하고 실패했던 명령 및 영향 범위 검증을 통과한 뒤 한 번 push한다. 이미 알려진 동일 수정의 실패를 남겨 둔 채 단계별 push하는 일을 줄인다. 서로 무관한 finding을 한 commit에 묶거나 review.yml 격리 규칙을 완화하지 않는다. CI에서만 재현되는 검증은 근거를 남기고 필요한 push를 허용한다.

branch 최신화는 별도의 readiness 분기로 다룬다. 현재 head에 대한 결정적 failure와 진행 중인 관련 검증이 없고 필요한 사람의 승인 상태가 확보되면 GitHub에서 최신 head/base/mergeability를 다시 조회한다. BEHIND이고 strict가 최신화를 요구하면 해당 head/base 쌍에 대해 실행 가능한 최신화 요청을 한 건 기록한다. 현재 코드에 강제 update-branch 호출은 확인되지 않았으므로 불필요한 runtime 명령을 제거한다고 주장하지 않는다.

review 중인 branch에 자동 rebase/force-push하거나 임의 merge commit을 만들지 않는다. 기존 저장소 git 정책에 맞게 담당자가 최신화를 수행하도록 요청하고, 같은 head/base를 기다리는 동안 중복 요청하지 않는다. 최신화 수행 직전에 main이 더 전진했다면 최신 관찰 base로 요청을 갱신한다. 실제 conflict는 담당자의 의미 확인과 해결이 필요하다.

최신화로 head/base가 바뀌면 기존 required gates를 정상 실행한다. 새 head에 옛 success를 복사하지 않으며 stale approval 정책도 그대로 적용한다. main이 다시 움직이면 같은 절차를 반복한다. 최신화를 딱 한 번만 한다는 보장은 없다. 한 번의 준비 완료 판단에 대해 중복 요청·불필요한 선행 최신화를 줄이는 정책이다.

보호 정책·배포·복원

활성 ruleset의 strict_required_status_checks_policy=true를 유지하고 아래 required contexts, integration_id, 승인 수, stale approval dismissal 및 bypass 정책을 변경하지 않는다.

  • test (python 3.12)
  • lint (ruff)
  • validate
  • severity gate (review + security)
  • maintenance gate (verdict + docs-updated)
  1. 기존 durable runtime에 retry 계획과 최신화 요청 식별자를 추가하고 회귀 테스트를 통과시킨다.
  2. staging PR에서 실패 job만 재실행하고 downstream이 올바른 결과를 집계하는지 확인한다. 실제 정책 실패에는 재시도가 발생하지 않아야 한다.
  3. pilot PR에 적용하여 동일 입력 job 재실행 수, 수정당 push 수, head/base별 최신화 요청 중복을 측정한다. ruleset 전후 비교가 동일해야 한다.
  4. 오분류나 중복 mutation이 발견되면 해당 retry 기능을 되돌리고 기존 수정/수동 복구 흐름으로 돌아간다. 보호 설정은 처음부터 유지되므로 rollback 때 검증 강도를 복원할 필요가 없다.

현재 저장소는 개인 User 소유로 GitHub Merge Queue 지원 조건에 맞지 않는다. 향후 조직 이전을 별도로 결정한다면 queue의 최신 합성 SHA에 대한 실제 통합 검증으로 최신화 부담을 옮길 수 있다. 현재 queue workflow에는 pytest 및 기존 required context가 모두 없으므로 단순 활성화는 불가능하다. 이번 제안은 조직 이전, queue 설계, trusted receipts/cache 시스템을 필요로 하지 않는다.

출처와 확인 범위

  • GitHub 재실행 문서: job/failed-job 재실행 및 원래 SHA/ref 유지.
  • GitHub CLI gh run rerun: --failed, --job 사용 및 job 식별자 주의.
  • GitHub Merge Queue 운영 문서: author branch 최신화 대신 queue 통합 검증, merge_group required checks 요구.
  • 실제 활성 ruleset API: 2026-09-09 읽기 조회. 저장소 접근 권한이 필요할 수 있다.
  • 검토한 review workflow.
  • 검토한 babysit-pr.

이 문서는 원인 분석과 구현 제안이다. GitHub 설정 및 CI/runtime 구현은 변경하지 않았다. strict 유지와 제안된 향후 동작을 구분했으며, 실제 재실행 비용의 정량 baseline은 아직 수집하지 않았다.

  • GitHub protected branches의 strict/loose 비교: loose는 build 횟수를 줄이지만 최신 base와의 비호환 위험이 있다.
  • 실제 gate 단독 실패 실행: upstream 실행 성공과 최종 verdict 승인이 다름을 확인.
  • 저장소 소유 형태 API: 조사 시 public, owner.type=User.

Before / After

Before (current state)

실패 job만 재시도할 수 있는 GitHub 기능을 babysit-pr이 명시적으로 활용하지 않는다. 현재 루프는 실패 분석 → 수정 → 로컬 검증 → commit/push가 중심이다. 새 push는 synchronize 이벤트를 발생시켜 여러 workflow를 다시 시작한다. main 최신화 요구의 직접 원인은 활성 ruleset의 strict_required_status_checks_policy=true다. Merge Queue workflow 파일은 있지만 운영 ruleset에는 merge_queue 규칙이 없다. 저장소는 public이지만 개인 User 소유로, 현재 GitHub Merge Queue 지원 대상이 아니다.

After (proposed state)

strict_required_status_checks_policy=true, 기존 required checks 5개, 승인 정책과 fail-closed 동작을 유지한다. 동일 입력의 확인된 일시적 실패만 GitHub native job retry로 복구한다. 같은 논리적 수정의 로컬 검증을 마친 뒤 한 번 push하고, branch 최신화는 다른 blocker가 해결된 시점에 최신 head/base를 확인하여 요청한다. 새로운 코드나 base에 대한 필수 검증은 생략하지 않는다.

Pros

  • 현재 strict 보호와 필수 검증을 그대로 유지하여 비용 절감 때문에 통합 보장을 낮추지 않는다.
  • 같은 SHA의 확인된 일시 장애는 성공한 독립 job을 반복하지 않고 복구한다.
  • 같은 수정의 불완전한 push와 준비 전 반복 최신화를 줄인다. 기존 durable runtime과 native retry를 사용해 별도 cache/merger를 만들지 않는다.

Cons

  • 실패 분류 및 요청 중복 방지를 위한 작은 runtime 상태가 추가된다. 기존 durable 저장소와 보수적인 allowlist로 범위를 제한한다.
  • 최신화를 마지막으로 미루면 마지막 검증이 완료되기까지 대기할 수 있다. main 변경이 계속되면 다시 최신화하고 검증해야 한다.

Limitations

  • 새 코드 또는 새 base에 필요한 검증은 절감 대상이 아니다. conflict가 없어도 strict가 요구하는 최신화와 gate 재실행은 유지한다.
  • 동일 SHA라도 외부 입력이 바뀌었거나 실패 원인이 불명확하면 자동 retry하지 않는다. 임의의 cross-SHA verdict 재사용은 하지 않는다.
  • 현재 개인 소유 저장소의 Merge Queue 미지원 문제를 이번 변경의 의존성으로 만들지 않는다. 조직 이전과 queue 도입은 별도 선택이다.
