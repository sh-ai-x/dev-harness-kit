Decision rule (3-axis)

For each gate, ask three questions in order:

  1. Does it cost provider tokens? (i.e. does it call an LLM judge — /dev-kit:review, /dev-kit:security, /dev-kit:maintenance?) If yes → Tier B (must stay remote). Severity review comments belong in GH Actions because that's where the provider tokens are intentionally spent and where the PR comments land.
  1. Does it consume significant local CPU/memory? (pytest tests/ on a large suite can run 30-120s + several GB RAM; cache-decay-audit runs a subset of pytest too.) If yes → Tier A optional (opt-in via config flag, NOT on by default). The user's local machine has bounded resources; the pre-push hook must not become a battery/CPU drain on every push.
  1. Does it fail in a way the developer can fix before pushing? (i.e. is the failure mode visible in the diff, commit message, or staged file content — not external state?) If yes → Tier A (local pre-push). The point is to prevent LLM judges from firing on a known-broken push. Tokens saved per caught failure: $1-3.
  1. Is it triggered by a merge event? (e.g. version-bump.yml fires on pull_request: closed after main merge.) If yes → Tier C (post-merge only). No pre-push mirror needed.

A gate is Tier A core iff: cheap locally (axis 2 = no) AND fixable pre-push (axis 3 = yes). A gate is Tier A opt-in iff: expensive locally (axis 2 = yes) AND fixable pre-push (axis 3 = yes). A gate is Tier B iff: costs provider tokens (axis 1 = yes). A gate is Tier C iff: post-merge trigger (axis 4 = yes).

Tier A — local pre-push (split: core vs opt-in)

Tier A core — RECOMMENDED DEFAULT (always on; cheap locally)

Recommended shipping scope: issue-sync only. This is the only stage that actually saves provider tokens; everything else in this proposal is opt-in.

GateLocal commandWall-clockCPU/memToken-saving
`issue-sync`tools/issue_sync.py pre-push --remote origin --base origin/main --strict~9s + 1 gh api per ref<10MB RSS$1-3 per caught stale-ref push

Tier A core wall-clock: ~9s on a warm tree. CPU/memory footprint: <10MB RSS (just the parser). Zero pytest, zero ruff, zero validate — until user opts in below.

Why issue-sync is the only recommended default: it is the only Tier A gate that catches a failure mode invisible to GH Actions' deterministic gates AND saves provider tokens by blocking the LLM judges. Other Tier A gates are token-neutral (they catch failures that GH Actions would catch anyway) or only marginally useful (faster feedback, but the failure doesn't waste tokens).

The `gh api` call in issue-sync is optional:

  • With --offline: parser emits the ref list and warns (does not fail). Developer runs the full check on push if they want the fail-fast signal.
  • Without --offline (default): runs the same gh api check as the workflow. The developer needs gh auth status green.

Headline win: Phase 1 alone saves $1-3 of provider tokens per stale-ref push (the PR #829 failure mode) at <10s wall-clock + negligible local resource cost. No opt-in config needed. Phase 2's opt-in stages (test/validate/lint) are for users who explicitly want to save more tokens at the cost of local CPU.

Why this is NOT a CI runtime optimizer

The proposal does not reduce GH Actions minutes. It only reduces the rate of red pushes. A developer who fixes a failing gate locally still pushes the green version to GH Actions, which then runs the same Tier-A gates (plus Tier B).

The only GH Actions savings are:

  1. Pushes blocked at pre-push never reach pull_request events.
  2. Fewer rerun calls on already-red workflows.

Both are second-order effects. The primary metric is developer time-to-fix, not GH Actions spend.

What this is NOT

  • Not a wholesale CI migration. No remote gate is removed.
  • Not a substitute for LLM judges / severity review. Tier B stays remote. PR comments from /dev-kit:review / /dev-kit:security / /dev-kit:maintenance must land in GH Actions because that's where the comments are posted.
  • Not a CI runtime cost reduction. GH Actions minutes per PR are unchanged. The win is provider token spend on caught Tier-A failures, not GH Actions minutes.
  • Not a mandate to migrate `test` / `validate` / `lint`. Those gates cost zero provider tokens and can stay in GH Actions. They land in hooks/pre-push.sh because they're already part of the orchestration; the user has explicitly said they're not the bottleneck.
  • Not a magic bullet for fork-PRs. fork-pr-review.yml is a different problem (GitHub security model — fork PRs can't access secrets) and stays as-is.
