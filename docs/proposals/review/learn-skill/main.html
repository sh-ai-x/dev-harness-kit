Executive summary

dev-harness-kit의 39개 스킬 중 "원본에서 추출해 새 산출물로 지속화"하는 루프가 부재합니다. 현재 가장 가까운 두 자매 — prune-propose(audit-only, telemetry에서 후보를 읽고 삭제 후보만 제안)와 ci-triage(audit-only, GitHub Actions 실패 시그니처를 case store에 영속화) — 모두 기존 표면을 정리하는 역할이지, 새 표면을 만들지는 않습니다.

본 proposal은 dev-kit 자체 discipline인 3-step state machine (gather → distill → approve-write)을 신규 영역에 적용해 이 갭을 메우는 신규 스킬 /dev-kit:learn을 추가합니다. 외부 영감 출처에 대한 언급은 일절 없으며, 모든 설계 결정은 dev-harness-kit의 기존 Iron Laws (L1~L8), rules/skill-authoring.md, tests/test_skill_governance.py의 SSOT에 근거합니다.

Net verdict: Phase 1 (4 파일) ADOPT, Phase 2 (1 파일 추가) DEFER until Phase 1 usage metrics. Net 토큰 델타 +345줄 (net-zero FAIL이지만 Phase 2 분리로 cherry-pick 표면 제한). Q3 2026 third-party 채택 0건 → /learn이 cherry-pick #1 (한도 2/quarter) PASS.

Problem statement

dev-harness-kit은 39개 스킬을 운영하지만, 다음 capability가 비어 있습니다:

  • "방금 한 일을 재사용 가능한 스킬로 �처"
  • "기존 트랜스크립트/파일/URL을 새 스킬로 변환"
  • "세션에서 반복 등장한 패턴을 영속화"

현재 사용자가 새 스킬을 만들려면 skills/<name>/SKILL.md를 수작업으로 작성해야 합니다. 이는 (a) rules/skill-authoring.md의 L6/L7 규칙을 모두 외워야 하고, (b) frontmatter 형식을 수동으로 맞추고, (c) 7개 canonical 섹션을 순서대로 채워야 하므로 30분+ 작업입니다.

prune-propose는 "추출→지속화"의 절반 — telemetry에서 패턴을 읽고 후보로 만드는 단계 — 은 자동화했지만, "원본 자유 텍스트에서 새 스킬 본문으로"의 절반이 비어 있습니다. 이 갭을 메우면 dev-kit이 사용 세션에서 학습한 패턴을 즉시 자원으로 변환할 수 있습니다.

옵션 A 선택 근거:

  • 코퍼스: 현재 세션 트랜스크립트는 가장 안전한 범위. 사용자 메모리 (~/.claude/projects/.../memory/feedback-*.md)까지 확장하면 ci-triage/SKILL.md L38에 명시된 "bad memory injection" failure cause가 켜집니다. feedback-minimal-action-on-vague-prompts.md도 silent defaulting을 경고합니다. 코퍼스 확장은 사용 데이터가 필요성을 입증한 뒤 별도 PR로.
  • PR 범위: 풀 디자인 5파일은 +485줄로 thin-harness discipline의 "harness stays thin" 게이트를 깨고, Phase 2 후보(parse_source.py)가 cherry-pick에 묶여 사용 데이터 없이 합쳐져 들어갑니다. Phase 1을 분리하면 cherry-pick 표면이 +345줄로 줄고, Phase 1 종료 후 usage 측정 → 효과 입증 시 Phase 2로 가는 게 gradual absorption 게이트에 부합합니다.
  • bare 호출: 옵션 A는 "트랜스크립트 없으면 AskUserQuestion"으로 silent fabrication을 거부. 옵션 B의 "현재 세션 자동 스캔"은 사용자 의도가 불분명한 상태에서 last-8-turn을 임의 distill하므로 feedback-minimal-action-on-vague-prompts.md 위반.

Recommended approach — `/dev-kit:learn` 설계

Skill metadata (skills/learn/SKILL.md)

---
name: learn
category: audit
alpha: state
description: Distill source text into a new SKILL.md with approval gate.
when_to_use:
  - User types /dev-kit:learn <free text>
  - User wants to convert a transcript/file/URL/observation into a new reusable skill
allowed-tools: Read Write Glob Grep WebFetch Bash AskUserQuestion
disallowed-tools: Edit Agent
model: sonnet
user-invocable: true
---
  • description 검증: 59자 (≤60 통과). 마침표 포함, 단일 문장, 마케팅 단어 없음.
  • alpha: state — 5개 deterministic 게이트가 알파. 모델이 변형 가능한 건 본문 산문뿐. prune-propose/ci-triage와 동일 카테고리.
  • Edit/Agent 제외 — 기존 파일 수정/하위 위임 금지 (mirrors ci-triage discipline).

State machine (3-step, dev-kit discipline 확장)

prune-propose/ci-triage의 3-step state machine을 신규 영역에 적용:

[1/3] GATHER
  입력: /dev-kit:learn <arg>, arg ∈ {empty, path, URL, prose}
  도구: Bash(argparse), Read(file), WebFetch(URL), Bash(grep logs/...jsonl)
  산출: source-locator + char count (quoted)
  ↓
[2/3] DISTILL
  모델이 후보 1~3개 본문 작성
  결정론: 후보별 G1~G5 통과
  모델 변형 가능: 본문 산문, 후보 이름(G4 통과 조건), 후보 수(1-3)
  산출: 후보별 PASS/FAIL 요약 + 위반 리스트 (quoted)
  ↓
[3/3] APPROVE-WRITE
  후보별 AskUserQuestion (4 옵션):
    (a) Write to skills/<name>/
    (b) Rename & retry
    (c) Skip
    (d) Abort all
  (a) → Write 1회 호출 → skills/<candidate>/SKILL.md
  산출: 작성된 경로 + git diff --stat (L3)

상태 영속화: 없음. 단일 슬래시 호출 안의 3-섹션 흐름 — in-context 변수만으로 충분. 영속 파일은 attack surface를 키울 뿐 UX 이득 없음.
