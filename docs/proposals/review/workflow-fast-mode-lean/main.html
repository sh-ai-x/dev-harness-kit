1. Design principle — correctness gates stay local, others defer to CI

Vibe mode is not "skip safety". It is "pay the safety cost once, in CI, instead of twice (local + CI)". The only gates that absolutely MUST run locally are the ones whose failure CI cannot recover from.

Gates fall into four categories:

CategoryExamplesPicker-eligible?Why
Correctnessstop_verify, secret_scan, intent_integrity (high), gh_ci_requiredNO — never shown, never offSub-agent silently succeeding on no-diff (issue #221 RC2), leaked credentials, high-severity finding pushed as PR — CI cannot recover the time already invested, OR the leak happens before CI sees it.
Styleslop_detector, maintenance (CC/OE/VM)YESLint / cosmetic. CI re-runs the same gates; nothing local-only is lost.
Quality/dev-kit:review verifier pass, /dev-kit:security (10-dim OWASP)YESMulti-pass LLM judge — local wall-clock's main culprit. .github/workflows/{review,security}.yml runs the same checks on push.
Processpre_commit_review (codex:review), /dev-kit:babysit-pr pollingYESHuman / loop time. Branch protection + GH-Actions required checks provide the same enforcement on push.

Two outcomes:

  • PR merged correctly with full strict review: same end state, less local time.
  • CI catches something local would have caught: developer fixes it; same end state, slightly later.

There is no path where CI merges without strict review but local would have caught it — because CI runs the same gates. The only thing fast/custom mode sacrifices is developer time, not correctness.

3. The /dev-kit:harness-mode skill

/dev-kit:harness-mode fast     # instant: all optional gates OFF, correctness gates ON
/dev-kit:harness-mode full     # instant: everything ON (also the SessionStart default)
/dev-kit:harness-mode custom   # interactive: walks the 6 optional gates via AskUserQuestion
/dev-kit:harness-mode show     # prints the currently resolved gate table, no prompts

custom issues two batched AskUserQuestion calls — 3 questions each, matching the practical limit for a single legible prompt screen:

Call 1 (Y/N gates):

#QuestionOptions
1Run the TDD scope judge locally before each build step?Keep it ON / Skip locally (defer to CI)
2Run slop-detector locally on each write?Keep it ON / Skip locally
3Run pre-commit codex:review before each commit?Keep it ON / Skip locally

Call 2 (Y/N + enum gates):

#QuestionOptions
4Run the maintenance (CC/OE/VM) gate locally?Keep it ON / Skip locally
5Local security scan depth?Full 10-dim OWASP fan-out / Quick single-dim summary / Skip locally
6/dev-kit:babysit-pr behavior this session?Full auto-fix polling loop / Manual: one gh pr checks dump + exit

Each answer writes directly into .dev-kit/harness-mode.session.json:gates.<name>. The skill then prints the resolved table (same format as full/fast) so the developer sees exactly what was chosen before continuing.

alpha: state per the L6 skill gate (tests/test_skill_governance.py) — the skill persists a session artifact and gates subsequent skill behavior from it, which is state by definition, not analysis or enforcement.

4. Session-scoped default — new window always starts full

A new SessionStart hook, hooks/session-start-harness-mode-reset.sh, unconditionally writes:

{"mode": "full", "gates": {}}

to .dev-kit/harness-mode.session.json at the start of every session — before the worktree auto-cut hook, loghooks installer, or any other SessionStart hook in this repo runs its own logic (order does not matter here since this hook only touches its own file). This guarantees:

  • Opening a new Claude Code window or Codex session always starts in full (strict) mode, regardless of what the previous session left behind.
  • fast or custom must be chosen explicitly, every session — there is no way to "leave fast mode on" by accident across a break.
  • The state file is NOT a project-level config; it lives in .dev-kit/ (already gitignored alongside other session/run state such as .dev-kit/trace/, .dev-kit/repair/), so it never gets committed and never leaks between developers sharing a clone.

Failure mode: if the hook fails to run (e.g. .dev-kit/ not writable), lib.harness_mode_state.read_state() falls back to mode=full when the file is missing or corrupt — the safe default either way.

5. Implementation sketch

# lib/harness_mode_state.py
STATE_PATH = Path(".dev-kit/harness-mode.session.json")
CORRECTNESS_GATES = frozenset({
    "stop_verify", "secret_scan", "intent_integrity", "gh_ci_required",
})

def read_state() -> dict:
    if not STATE_PATH.exists():
        return {"mode": "full", "gates": {}}
    try:
        return json.loads(STATE_PATH.read_text())
    except (OSError, json.JSONDecodeError):
        return {"mode": "full", "gates": {}}  # corrupt file -> safe default

def write_state(mode: str, gates: Optional[dict] = None) -> None:
    STATE_PATH.parent.mkdir(parents=True, exist_ok=True)
    atomic_write_json(STATE_PATH, {"mode": mode, "gates": gates or {}})

def resolved_gate(name: str) -> str:
    if name in CORRECTNESS_GATES:
        return "on"  # hardcoded — no state file value can override this
    state = read_state()
    if name in state.get("gates", {}):
        return state["gates"][name]
    return "on" if state.get("mode") == "full" else "off"
# hooks/session-start-harness-mode-reset.sh
python3 -m lib.harness_mode_state write full
# hooks/slop-detector.sh — first 3 lines
if [ "$(python3 -m lib.harness_mode_state get slop_detector)" = "off" ]; then
  echo "slop-detector: opted out via harness-mode" >&2
  exit 0
fi

Sub-agent preamble injection (unchanged shape from earlier iterations):

AC: see step file. 3-cycle self-fix max.
Gates in effect: stop_verify=ON, secret_scan=ON, tdd_scope_judge=OFF (harness-mode=fast).
Do not write tests for non-production code unless the step file asks.
If stop_verify or secret_scan fires, treat as a hard stop.

7. Why this beats the earlier all-YAML profile framework

The first (over-engineered) draft of this proposal added a new YAML schema (gate_definitions + profiles + active_profile), a resolver module, a config-management skill, and updates to 5 existing skills plus N hooks — 12+ file changes for a project-level, hand-edited config file.

This version keeps the same underlying mechanism (one small state module, correctness gates hardcoded) but replaces "hand-edit a YAML profile" with "answer up to 6 quick questions via the tool you already have open" and replaces "project-level persistent config" with "session-scoped, resets every window". Both changes reduce the blast radius of a wrong or forgotten setting: a bad YAML edit persists until someone notices it in a diff; a bad interactive answer only lasts until the next session opens.

8. Out of scope (intentionally)

  • Per-branch auto-detection. The developer runs /dev-kit:harness-mode explicitly every session by design (section 4).
  • Persisting a project-level DEFAULT mode across sessions/developers. Every session starts full; there is no .dev-kit/harness-mode.yaml equivalent to hand-edit and commit.
  • Telemetry on "fast/custom-mode-shipped work caught by CI". Ship the mechanism first; measure second.
  • Agent model selection. Iron Law 5 is unchanged.
  • GH-Actions workflow changes. CI is the safety net; local mode selection is a developer convenience only.
  • Gate dependency rules in the picker UI (e.g. auto-forcing maintenance on when security_owasp=full). If needed later it lives in resolved_gate(), not in the AskUserQuestion prompts.

Before / After

Before (current state)

The dev-harness-kit build pipeline runs the full local gate stack by default: TDD scope judge, intent-integrity pre-build gate, slop-detector, pre-commit codex:review, and /dev-kit:babysit-pr polling loop. All-or-nothing today.

A "vibe" local iteration loop (small change, manual smoke test, no PR) pays for the full gate stack every commit. Existing escape hatches (DEV_KIT_SKIP_TDD=1, --skip-blocked, --fast on /dev-kit:review) are scattered across env vars, CLI flags, and sibling skills with no common shape and no way to express "skip every optional local gate at once", let alone "skip only these three gates, keep those two".

  • lib/execute.py:78-90: DEV_KIT_BUILD_AGENT env override (claude | codex)
  • lib/execute.py:404-407: only --skip-blocked and --push flags exist on the runner today
  • skills/review/SKILL.md:30: --fast flag scoped to one skill (skip verifier only)
  • hooks/index.md: tdd-guard, slop-detector, secret-scan, stop-verify — no per-project opt-out path
  • Bash tool contract: "the working directory persists between commands, but shell state does not" — a plain export DEV_KIT_FAST_MODE=1 cannot reliably carry across tool calls, ruling out a pure env-var mechanism for a multi-turn session

After (proposed state)

One new skill, /dev-kit:harness-mode, with three sub-commands: fast, full, custom. fast and full apply instantly — no prompts. custom walks the developer through the optional gates using the native interactive choice tool available in the runtime (AskUserQuestion in Claude Code), batched 3 questions per call so no single prompt exceeds a comfortable choice count. The resolved mode is written to a small session-scoped state file, .dev-kit/harness-mode.session.json, that every gated skill reads on each invocation. A new SessionStart hook resets that file to {"mode": "full"} at the start of every session — opening a new window always starts strict; fast or custom must be chosen explicitly, every session. Correctness gates (stop_verify, secret_scan, intent_integrity-high, gh_ci_required) are never presented as options in the picker and never turn off, regardless of mode.

Pros

  • Single skill (/dev-kit:harness-mode) covers all three needs the user asked for: an instant fast toggle, an instant full toggle, and a granular custom picker — no YAML editing, no web form.
  • Interactive picker reuses the runtime-native choice tool (AskUserQuestion) instead of building a bespoke UI. Zero new UI surface, zero new dependency.
  • Batching at 3 questions per AskUserQuestion call keeps each prompt legible; 6 optional gates fit in 2 calls.
  • Session-scoped default (reset to full on every SessionStart) means forgetting to turn fast mode back off cannot leak into the next session, unlike a project-level DEV_KIT_FAST_MODE=1 env var a developer forgets they exported.
  • Correctness guarantee unchanged from v2: the four mandatory gates (stop_verify, secret_scan, intent_integrity-high, gh_ci_required) are hardcoded in lib.harness_mode_state.resolved_gate() to always resolve "on" — not even a hand-edited state file can disable them.
  • GH-Actions workflows untouched — push still runs the full strict gate set, so a fast/custom-mode commit cannot merge without the rigorous review.
  • Legacy --fast flag / DEV_KIT_FAST_MODE env var preserved as scriptable shortcuts that resolve to the same underlying state file, so CI-invoked or headless runs are not forced through an interactive prompt.

Cons

  • The interactive picker (custom) only works in a session where AskUserQuestion (or the runtimes equivalent) is available — not in a fully headless/CI invocation. fast and full` remain the non-interactive fallback for that context.
  • A new SessionStart hook is one more file competing for the SessionStart slot; needs to compose cleanly with the existing worktree auto-cut and loghooks SessionStart hooks already registered in this repo (hooks/index.md).
  • Session-scoped reset means a developer running many short sessions in one working day re-picks custom mode every time they want it — a deliberate trade-off (safety over convenience) but a real repeated cost for heavy fast-mode users.
  • Two mode-selection paths exist (interactive skill vs. legacy flag/env var) — needs a one-line precedence doc so a script that sets DEV_KIT_FAST_MODE=1 and a developer who ran /dev-kit:harness-mode custom in the same session do not silently fight each other. Resolution: skill-mutated state file is the source of truth; the legacy flag/env var is read by lib.harness_mode_state.resolved_gate() ONLY as a fallback default when no session file exists yet.

Limitations

  • Fast/custom mode cannot speed up GH-Actions itself; CI wall-clock is unchanged. It only removes local-only gates.
  • Fast/custom mode cannot change agent model selection (Iron Law 5: opus for design, sonnet for code). Model is fixed by the parent task, not by harness mode.
  • Fast/custom mode does NOT prevent merging a fast-mode PR — it only skips local gates. CI still enforces. This is the intended contract, not a gap.
  • No per-branch auto-detection (e.g. "fast on feat/*, full on main"). Out of scope; the developer runs /dev-kit:harness-mode explicitly every session.
  • No telemetry on "how often does fast-mode-shipped work get caught by CI". Ship the mechanism first; measure second.
  • The picker cannot express dependencies between gates (e.g. "if security_owasp=full, force maintenance=on"). All 6 optional gates are independent toggles/enums; if a dependency rule is needed later it goes in lib.harness_mode_state.resolved_gate(), not the picker UI.
