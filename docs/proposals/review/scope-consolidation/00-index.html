Why one canonical reference

Every operator asks the same five questions:

  1. Where do I put my personal preferences? (user scope)
  2. Where do I tell this project which kit to use? (project scope)
  3. Where do I put my private overrides within a project? (local scope)
  4. Which mode (full / lite / undev) is right for this project?
  5. Why is destructive-confirm firing in a repo that never ran ci-setup?

Until this PR, each of those questions had an answer scattered across CLAUDE.md, hooks/index.md, iron-laws/index.md, the bootstrap skill, and tribal knowledge. The answer also depended on which plugin was loaded (dev-kit vs dev-kit-lite), so the same project could behave differently on two operators' machines.

docs/scopes/ answers all five questions from one directory, indexed by one word: scope.

The three scopes, restated crisply

ScopeFileGitLifetimeOwnerUsed for
User~/.claude/settings.jsonn/amachineoperator onlypersonal prefs, keybindings, statusline, universal allows

Local<proj>/.claude/settings.local.jsongitignoredyour checkoutoperator onlypersonal override of project scope, debug flags

The rule that resolves 90% of confusion: the smallest scope that satisfies the need wins. If a setting is purely personal, it goes in user scope. If it must be team-shared, it goes in project scope. If it is your private override of a team setting, it goes in local scope.

The three modes

DEV_KIT_MODE is a project-scope env value with three legal values:

  • full — current dev-kit (30+ skills, 30+ hooks, multi-session/multi-agent). Default if unset.
  • lite — 7-skill / 7-hook subset for 4-hour MVP sprints with a 6-person team. The follow-up PR makes this subset run from the same plugin.
  • undev — plugin not enabled. Silent default for non-dev repos. Already true today, but now it is explicit.

Resolution order (highest wins):

  1. $DEV_KIT_MODE env var in the shell
  2. env.DEV_KIT_MODE in <proj>/.claude/settings.json
  3. Default = full

Per-session override without touching files: DEV_KIT_MODE=lite claude --plugin-dir <repo>.

The leak, in one paragraph

The bug we are closing: enabledPlugins.dev-kit@dev-kit: true at the user layer fires the kit's hook stack in every project on the machine, including ones that never opted in. The fix is structural — move the enabledPlugins line from user to project scope, and rely on extraKnownMarketplaces at user scope only so slash commands resolve.

This PR documents the fix. The follow-up PR will offer a one-shot migration script.

Why dev-harness-kit-lite becomes a follow-up

Unifying dev-harness-kit-lite into the main repo requires runtime changes — a mode gate inside every hook, a mode resolver, and /dev-kit:mode skill. Those are non-trivial and risky to ship in the same PR as the docs because reviewers cannot tell which change caused a regression.

The doc-first sequencing lets reviewers validate the contract (templates + decision tree) before any code reads from it. The follow-up PR will then write lib/mode.sh, gate every hook, and add the /dev-kit:mode skill — all using these templates as their input.

Adoption path

Step 0 — Land docs (this PR). Reviewers verify the scope/mode contract is clear and the templates are correct.

Step 1 — Update bootstrap. /dev-kit:bootstrap reads from docs/scopes/templates/settings.project.<mode>.json instead of writing inline JSON. Drop-in for projects that already ran bootstrap.

Step 2 — Add /dev-kit:mode skill. Read/write DEV_KIT_MODE in env block. No hook changes yet.

Step 3 — Wire hook mode gate. Add lib/mode.sh, source it at the top of every hook, short-circuit if $DEV_KIT_MODE does not match the hook's required mode.

Step 4 — Deprecate lite repo. Tag sh-ai-x/dev-harness-kit-lite v0.1.0 as final, add a DEPRECATED banner pointing at dev-kit + mode=lite, archive after 90 days.

Step 5 — Migrate users. One-shot script: claude plugin uninstall dev-kit@dev-kit && claude plugin install dev-kit@dev-kit to drop stale cache versions.

Each step is independently reviewable and reversible. None of them weakens the safety rails of the existing kit.

Tests and verification

This PR is docs-only, so the verification is review-side:

  • Markdown renders correctly on GitHub (no broken links).
  • JSON templates parse with jq (no trailing commas, valid syntax).
  • .gitignore-snippet applies cleanly to a fresh repo (verified by git check-ignore).
  • Cross-references resolve (every internal link points to an existing file).

The follow-up runtime PR will add tests/test_mode_resolution.sh (3 modes × 3 scope levels = 9 cases) and tests/test_hook_filtering.sh (every hook × 3 modes = N cases).

Why this design wins alternatives

AlternativeWhy rejected
Put scope docs in each plugin's README.mdDrift between two repos; operators read whichever repo they installed, never the other.
One giant docs/configuration.mdMixes scopes, modes, hooks, permissions into one wall of text; reduces findability.
Three separate plugin manifests (dev-kit-full, dev-kit-lite, dev-kit-off)Triples marketplace surface area; mode becomes an install-time decision instead of a per-session env var; harder to evolve.
Single docs/scopes/ with no templatesOperators still copy-paste from examples; drift returns within a week.

The chosen design — one directory, three scopes, three modes, six templates — matches the three scopes of Claude Code settings and the three usage classes (full / lite / undev) without inventing new abstractions.

Before / After

Before (current state)

Today, dev-harness-kit ships reference docs for plugin hooks, iron laws, skills, and CI templates, but nothing dedicated to the three Claude Code settings scopes (user, project, local) or to plugin mode selection (full / lite / undev). As a result, the same questions are answered inconsistently across docs, and the answer changes depending on which guide the operator reads.

Concretely:

  • ~/.claude/settings.json is treated as the default place to enable plugins, but the user layer is machine-global — anything enabled there fires in every project, including scratchpads and non-dev repos. This causes the observed leak where dev-kit-lite's destructive-confirm.sh fires inside dev-harness-kit/ despite no project-level opt-in.
  • <project>/.claude/settings.json is the right place for a project's plugin choice, but no canonical template exists. Operators copy-paste from old examples, drift appears, and .claude/settings.local.json is sometimes committed because the project's .gitignore was never extended.
  • The "lite" plugin is published as a separate repo (sh-ai-x/dev-harness-kit-lite), but the lite assets are a strict subset of the full kit plus 5 role rules and 7 templates. Maintaining two repos diverges them over time; the same destructive-confirm.sh already exists in three places (full kit, lite, and stale cache versions).
  • The phrase "undev" (silent, no dev hooks) is not defined anywhere. Non-dev projects inherit the user-scope's leaked plugins, which is the bug, not the feature.

Evidence

  • ~/.claude/settings.json has "enabledPlugins": { "dev-kit@dev-kit": true, ... } at the user layer, so the kit fires in every project on this machine.
  • ~/.claude/plugins/cache/ contains 6 stale dev-kit/dev-kit/<sha> versions plus dev-kit-lite/0.1.0/; find ... -name destructive-confirm.sh returns 5 instances and worktree-guard.sh returns 8 — the cache itself is part of the leak surface.
  • hooks/index.md and iron-laws/index.md reference plugin modes implicitly but never explain how an operator sets or changes the mode.
  • .claude/settings.local.json is committed in this repo because .gitignore only ignores .claude-plugin/plugin/hooks/.strict and .claude/commands/ — the local-scope file leaks into the team-shared scope.
  • docs/proposals/ has no entry under scope-consolidation/ and docs/scopes/ does not exist.
  • sh-ai-x/dev-harness-kit-lite is a separate marketplace entry with 7 skills + 7 hooks; ~80% overlap with the full kit, but with no shared mode contract.

After (proposed state)

A single canonical reference directory docs/scopes/ answers every "which scope do I edit?" and "which mode am I in?" question from one place. The directory contains seven markdown files (decision tree + per-scope reference + modes + troubleshooting) and six JSON / dotfile templates (settings.user.json, settings.project.{full,lite,undev}.json, settings.local.json, and a .gitignore-snippet).

Every existing cross-reference (CLAUDE.md, iron-laws/index.md, hooks/index.md, README.md) gains a single one-line link into docs/scopes/. /dev-kit:bootstrap and /dev-kit:ci-setup are documented as the consumers of these templates — they read from docs/scopes/templates/ and write the matching file into the target project.

No runtime behavior changes in this PR. It is docs + templates only. Runtime unification (mode picker skill, lib/mode.sh, repo deprecation of dev-harness-kit-lite) is a follow-up PR that consumes these templates as its contract.

Pros

  • Single address (docs/scopes/) answers every scope/mode question — operators stop copy-pasting stale examples.
  • Templates are versioned with the kit, so bootstrap and ci-setup can read from a single source of truth.
  • Explicitly documents undev as a first-class mode, making the silent default intentional instead of accidental.
  • Reduces drift: any project that runs /dev-kit:bootstrap gets the right scope config in one command.
  • Net-negative file count when paired with the planned follow-up PR that deletes dev-harness-kit-lite (~25 fewer files repo-wide).
  • No runtime behavior change in this PR — purely additive documentation, zero blast radius for existing consumers.

Cons

  • Adds 13 new files to the repo; operators who never read the docs gain nothing and pay the maintenance cost.
  • Cross-references in CLAUDE.md, iron-laws/index.md, hooks/index.md must be kept in sync — drift here defeats the purpose.
  • Templates codify today's best practice; if the operator surface area changes (e.g., a fourth mode is added), every template must be revisited.
  • The lite template assumes the full plugin is enabled with DEV_KIT_MODE=lite; until the follow-up PR lands, running /dev-kit-lite:bootstrap will still try to install a separate lite plugin.

Limitations

  • This PR is docs + templates only. It does not add a /dev-kit:mode skill, lib/mode.sh, or runtime hook filtering — those ship in the follow-up PR.
  • It does not archive dev-harness-kit-lite or remove it from any user's extraKnownMarketplaces. That is also the follow-up PR, gated on user adoption of the unified mode approach.
  • It does not delete the 6 stale dev-kit/dev-kit/<sha> cache entries; that is a one-shot claude plugin uninstall && install on each operator's machine.
  • It does not retroactively fix any project that has dev-kit@dev-kit: true at the user layer — operators must opt each project into the right template manually.
