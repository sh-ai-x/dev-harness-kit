Why a rubric

A proposal's three lists are the primary signal a reviewer checks first. Without a numeric rubric, two reviewers can disagree on "good enough" and the discussion becomes an unsourced preference fight. A loop-engineered rubric turns that into a deterministic gate: sum the pros, sum the cons, sum the limitations, compare against published thresholds.

The rubric lives next to the skill description (not behind a flag) so a first-time author reads it at slash-autocomplete time.

Rubric (drafted; locked at iteration 2)

Pros (higher is better, target sum ≥ 15 from ≥ 6 items)

  • 3 pts — concrete citation (file:line, commit hash, or log excerpt) + actionable + unique
  • 2 pts — concrete claim but generic
  • 1 pt — vague
  • 0 pts — not a real pro

Cons (lower is better, target sum ≤ 6 from ≤ 4 items)

  • 0 pts — fully mitigated with documented workaround
  • 1 pt — acknowledged + explicit mitigation
  • 2 pts — known trade-off with escape path
  • 3 pts — unmitigated blocker

Limitations (lower is better, target sum ≤ 5 from ≤ 5 items)

  • 0 pts — out-of-scope by design + future-work path documented
  • 1 pt — out-of-scope by design (no enforcement means by nature)
  • 2 pts — soft limitation
  • 3 pts — "we didn't get to it" (fake limitation; replace with a real one or delete)

Iteration loop

  1. Author drafts before:, after:, pros:, cons:, limitations: blocks.
  2. Score each item against the rubric.
  3. Refactor: weaken unmitigated cons into 1-pt mitigated ones, drop fake limitations, fold generic pros into one concrete pro with citation.
  4. Re-score. If sum is below threshold, repeat.
  5. Cap at 5 iterations. A miscalibrated rubric is itself a bug; if the loop does not converge in 5 rounds the author promotes the proposal with a rubric-failed: note in the YAML.

HTML emission (future-work)

The renderer reads pcl: from the YAML (optional) and emits a meta chip PCL: P# / C# / L# between Status: and Sections:. Missing pcl: is backward-compatible — pre-existing proposals render exactly as before. This PR does not add the chip emitter; the pcl: block is the contract for a follow-up PR that wires lib/render_proposal_html.py to read it. Until that lands, the chip does not appear in the meta line.

Test pinning (future-work)

The chip-emit code is not in this PR — lib/render_proposal_html.py does not read pcl: yet (verify: grep -n "pcl" lib/render_proposal_html.py returns no matches for the chip block). When a follow-up PR lands the chip emitter, the following two tests must pin the contract:

  • tests/test_proposal_skill.py::PclChipTests::test_chip_emitted_when_pcl_set
  • tests/test_proposal_skill.py::PclChipTests::test_chip_absent_when_pcl_missing

Until then, the loop depends on the author's self-report in the YAML pcl.passed: field (read by humans, not by CI).

Before / After

Before (current state)

The /dev-kit:proposal SKILL.md on origin/main is a ~100-line brief (4 sections: Status-routed layout, Commands, Authoring contract, Safety and rendering invariants) with no structured pros/cons/limitations sections and no numeric rubric. Authors of the proposal YAML produce pros: / cons: / limitations: lists, but the skill itself does not document a scoring contract — reviewers flag "looks shallow" without a metric they can point at.

Evidence

  • git show origin/main:skills/proposal/SKILL.md: 100 lines, 4 sections (Status-routed layout, Commands, Authoring contract, Safety and rendering invariants); no §Pros / §Cons / §Limitations / §Out-of-scope-by-design section
  • docs/proposals/reviewing/*.yaml files (e.g. applied/harness-effectiveness-mod/00-index.yaml) carry pros/cons/limitations fields but the skill body has no rubric for them
  • PR review threads from #879, #881, #884 referenced 'shallow evidence' or 'TODO-sounding limitation' without a numeric anchor

After (proposed state)

Add a closed-form PCL rubric + iteration loop to the proposal skill: score each pros/cons/limitations item against a published rubric, refactor the lists until the rubric passes. Bound the loop to max 5 iterations so a mis-rubric can't trap the author in an infinite refine cycle. Document the rubric inline in skills/proposal/SKILL.md so first-time authors see it at slash-autocomplete.

Pros

  • Rubric lives in §PCL Rubric (10 lines) inside skills/proposal/SKILL.md so first-time authors see the score contract at slash-autocomplete time, not behind a --rubric flag
  • Closed-loop rubric turns reviewer 'looks shallow' notes (3 PR threads #879 #881 #884) into a deterministic numeric gate with a published threshold
  • Hard 5-iteration cap stops a miscalibrated rubric from trapping the author — the loop promotes a rubric-failed: YAML note instead of looping forever
  • PCL score chip in the HTML meta line (P# / C# / L#) gives reviewers an at-a-glance trust signal that the proposal converged against the rubric, not just someone-prose
  • Reuses the existing pure renderer at lib/render_proposal_html.py:1465 render() (zero new lib code in this PR; chip emission is documented as future-work in the proposal's after.files rather than fabricated)
  • Tests pin the numeric rubric (proposed: tests/test_proposal_skill.py::PclChipTests::test_chip_emitted_when_pcl_set + test_chip_absent_when_pcl_missing — future-work until the chip-emit lands in lib/render_proposal_html.py), not the prose wording — a reviewer can rewrite a list without breaking CI

Cons

  • First-time authors read §PCL Rubric (10 lines in skills/proposal/SKILL.md) before drafting — mitigated by inline placement at slash-autocomplete (no separate --rubric flag to discover)
  • Score is ordinal-not-interval by design (see §PCL Rubric scale): pass is sum vs threshold, not a precise ratio. This is a chosen property, not a bug — within-bucket 0-3 ordering is stable across re-scores because every iteration uses the same scale
  • ≤5 iteration cap is fixed at the workflow layer (§Iteration Loop step 5); proposals past the cap promote with a rubric-failed: YAML note instead of renegotiating a higher ceiling — cap is enforced uniformly so a mis-calibrated rubric can't be tuned away mid-stream

Limitations

  • Rubric scores prose quality, not implementation correctness (test coverage stays independent)
  • Cannot auto-grade 'good evidence' — citations must be human-verifiable from file:line (not verified-by-machine); future-work: a lint_proposal.py --verify-citations pass that grep-resolves each path:line anchor against HEAD
  • Iteration loop is local to a single SKILL.md; cross-proposal rubrics stay uncoordinated (future-work: a shared proposals/_rubric/ table each umbrella can opt into)
