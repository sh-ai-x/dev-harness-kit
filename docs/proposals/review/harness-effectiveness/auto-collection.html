Why one metric, not five

The 5-component scorecard in lib/harness_effectiveness.py is a research framework: it tells you what is and is not measurable, with honest INSUFFICIENT_EVIDENCE where evidence is missing. That is correct behavior for a reducer that must never invent numbers. But it is the wrong shape for a CI gate: a gate needs a single, reliable number whose absence means "the harness is broken", not "the harness has insufficient evidence for this corner".

subject_observability is that number. It is already defined at lib/harness_effectiveness.py:465-518, has a denominator (every step.started event in the corpus), and is meaningful at 0 (no subject ever terminates) and at 1 (every subject terminates). The threshold 0.95 is the smallest value at which the harness can credibly claim "we know where our work ended".

The other 4 components remain in the report for /dev-kit:evaluate and /dev-kit:harness-effectiveness. They are observable but not enforced.

The producer fix: try/finally context manager

Today lib/execute.py and the SessionEnd hook emit step.started and step.completed as separate append_event calls. Every code path that does not reach the second call (exception, interrupt, timeout) leaves a started subject without a terminal.

The fix is a context manager in lib/trace_log.py:

from contextlib import contextmanager

@contextmanager
def step(subject_id, *, stage="unknown", parent_id=None, run_id=None,
         workflow_id=None):
    _, started_id = append_event(root, {
        "event_id": new_event_id(),
        "event_type": "step.started",
        "subject_id": subject_id,
        "stage": stage,
        "parent_id": parent_id,
        "run_id": run_id,
        "workflow_id": workflow_id,
        "outcome": "started",
        "source": "trace_log.step",
        "evidence_ref": {},
        "ts": now_utc(),
    })
    outcome = "passed"
    try:
        yield started_id
    except Exception:
        outcome = "failed"
        raise
    except BaseException:
        outcome = "interrupted"
        raise
    finally:
        try:
            append_event(root, {
                "event_id": new_event_id(),
                "event_type": "step.completed",
                "subject_id": subject_id,
                "stage": stage,
                "parent_id": started_id,
                "run_id": run_id,
                "workflow_id": workflow_id,
                "outcome": outcome,
                "source": "trace_log.step",
                "evidence_ref": {},
                "ts": now_utc(),
            })
        except Exception:
            pass  # telemetry must not change workflow outcome

Every existing call site migrates from

append_event(root, {"event_type": "step.started", ...})
try:
    ...
except Exception:
    ...
append_event(root, {"event_type": "step.completed", ...})

to

with step(subject_id=..., stage=..., parent_id=..., run_id=...,
          workflow_id=...) as sid:
    ...

After migration every started subject terminates regardless of return path. The live corpus (currently 0.4%) moves to ≥ 0.95 on the next snapshot.

Cost model

OperationPer-call cost
lib.trace_log.read_events over 54k events~80ms
lib.harness_effectiveness.build_report~50ms
archive() write (atomic, gzip on rotate)~5ms
bin/collect-effectiveness.sh --mode=ci total~135ms
step() context manager per body~5ms (2 append_event + dict alloc)

Total SessionEnd overhead: ~135ms one-time. Total CI overhead: ~200ms per PR. Total per-step overhead: ~5ms (negligible vs typical step duration of seconds).

For comparison, the existing hooks/secret-scan.sh PostToolUse hook costs ~200ms on every Write. SessionEnd is strictly less frequent.

Verification plan

Every gate uses quoted evidence (Iron Law L3):

  1. pytest -q tests/test_subject_observability.py — quoted exit code + 12 test counts.
  2. Live metric: after the migration, run /dev-kit:harness-effectiveness and quote components.measurement_integrity.submetrics.subject_observability.coverage ≥ 0.95.
  3. Live CI gate: open a PR with a synthetic low-ratio event, quote the failing subject-observability check-run with the threshold in the message.
  4. Live statusline: enable subject_observability.show_in_statusline: true, quote the status line showing [subj-obs NN.N%].
  5. History rotation: append 250 snapshots, quote head file at 50 lines and tail gzipped.

Rejected alternatives

  • 5-component CI gate. The reducer reports INSUFFICIENT_EVIDENCE for 3 components today; gating on those deadlocks every PR. Gating on ROT alone is workable but opaque (a reviewer must read each component's findings). One explicit metric is sharper.
  • Per-tool-call `step.completed` in PostToolUse. Couples telemetry to the harness's tool surface; the context manager decouples it.
  • Tighten the threshold to 0.99. Too strict for the first ship; 0.95 leaves room for genuine edge cases. Configurable per project.
  • 5 distinct history files (one per component). Premature: one metric, one file. Per-component history is a follow-up if the team wants to gate other components later.
  • A separate `/dev-kit:harness-metrics` skill. Forbidden by the umbrella's own §3 ("별도 metrics skill ... 만들지 않는다"). The bin script is enough.

Open questions for the reviewer

  1. Threshold default 0.95. Right starting value, or should v1 ship at 0.90 (laxer) / 0.98 (stricter)? Configurable per project via subject_observability.threshold; default is the question.
  2. Per-subject exemption list. Out of scope for v1, but worth filing as a follow-up if the team uses async background jobs whose subjects legitimately never terminate in this snapshot.
  3. Cross-host aggregation. Out of scope here; a follow-up bin/collect-effectiveness-sync.sh could add a syncable JSON-per-snapshot stream. The data model is already shaped for it.
  4. Schema version bump. No bump needed (schema_version 3 already carries the subject_observability submetric per issue #702). Worth a sanity check that no consumer assumes an older shape.

Before / After

Before (current state)

The harness emits 54,307 events across 53,301 started subjects. Only 210 of those started subjects ever reached a terminal event. Every other subject (53,091) was started by a tool call or session boundary but never finished — the harness has no record of how they ended. The reducer already computes this gap as the subject_observability submetric at lib/harness_effectiveness.py:465-518: a

symmetric Jaccard ratio |started ∩ terminal| / |started ∪ terminal|. Today the

ratio is 0.4% — effectively zero.

Three structural problems compound the gap:

  1. The producer side leaks started subjects without terminals (every exception / interrupt / timeout path drops the terminal step.completed).
  2. The collector is manual. lib/harness_effectiveness.build_report is invoked only when a human types /dev-kit:harness-effectiveness or runs /dev-kit:evaluate. No SessionEnd / Stop / PostToolUse hook calls it.
  3. There is no enforcement. Even when the ratio is 0.4%, no CI step blocks a PR that widens the gap. The number is observable, not actionable.

Evidence

  • Live (2026-09-08, this checkout): subject_observability.coverage 0.004, finding "53,091 of 53,301 started subject(s) never reached a terminal event".
  • Producer gap: lib/execute.py emits step.started per build step but step.completed only on the success branch. Error / interrupt / timeout paths leave the subject open.
  • Producer gap: no PostToolUse hook emits step.completed for tool-call-scoped subjects. A Bash tool call that runs pytest opens a logical subject but never closes it.
  • Session-end pair is complete (hooks/session-start-check.sh:74-75 + hooks/trace-session-end.sh:62) but covers the session subject only — not the tool-call and step subjects.
  • No auto-collector: grep -rn "harness_effectiveness" hooks/ bin/ returns zero hits in the executable surface.
  • No CI step: find .github/workflows -name "*.yml" -exec grep -l "harness_effectiveness" {} \; returns zero matches.
  • No history: ls .dev-kit/trace/effectiveness-*.json* returns ENOENT.
  • No HUD: commands/statusline.md references model / tokens / cache / runtime only; no effectiveness tile.
  • Live scorecard confirms the gap surfaces: measurement_integrity.status INSUFFICIENT_EVIDENCE because event_coverage collapses when started subjects never terminate (lib/harness_effectiveness.py:543-566). Fixing the gap fixes the parent score.

After (proposed state)

One metric. One producer fix. One collector. One CI gate. One optional HUD tile. Five moving parts; one source of truth.

The metric: subject_observability (already defined at lib/harness_effectiveness.py:465-518). Always has a denominator when events exist. Range [0, 1]. Threshold 0.95 in .dev-kit/state.json (subject_observability.threshold).

The producer fix: a single try/finally context manager step(subject_id, ...) in lib/trace_log.py that emits step.started on __enter__ and step.completed on __exit__ regardless of success / exception / interrupt. Every existing emitter of step.started migrates to with step(...): .... The migration is mechanical.

The collector: one shell entrypoint bin/collect-effectiveness.sh that calls lib.harness_effectiveness.build_report + archive() (one new lib function) and writes .dev-kit/trace/effectiveness-latest.json + appends .dev-kit/trace/effectiveness-history.jsonl.

The auto-triggers: SessionEnd / Stop (always), pr-verify CI step (always), /dev-kit:evaluate (always — uses the same wrapper). All three consume the same file.

The CI gate: bin/collect-effectiveness.sh --mode=ci exits non-zero iff subject_observability < threshold. Single numeric comparison. No judgment.

The HUD: status-line tile [subj-obs NN.N%] reading effectiveness-latest.json. Off by default; opt-in via subject_observability.show_in_statusline: true in .dev-kit/state.json.

No new event types. No new producers. No schema version bump. The proposal changes WHEN the reducer runs and WHO surfaces its output. The reducer's 5-component scorecard remains untouched and continues to be reported by /dev-kit:evaluate and /dev-kit:harness-effectiveness for analysis; only subject_observability is gated.

Pros

  • One metric. One producer fix. One collector. One CI gate. One HUD tile. Smallest surface that satisfies "measured reliably".
  • The metric already exists (lib/harness_effectiveness.py:465-518) and is hermetic. This proposal only promotes it to the user-facing gate.
  • The producer fix is a try/finally context manager — one mechanical pattern. After migration every started subject terminates regardless of return path.
  • Auto-collection is unconditional: SessionEnd, pr-verify, evaluate, statusline all consume the same .dev-kit/trace/effectiveness-latest.json written by bin/collect-effectiveness.sh. One source of truth.
  • CI gate is a single numeric comparison. bin/collect-effectiveness.sh --mode=ci exits 1 iff subject_observability < 0.95. No judgment, no findings, no ambiguity.
  • The history file (.dev-kit/trace/effectiveness-history.jsonl) gives a trend line for free. A 1-line jq query over effectiveness-latest.json answers "are we drifting?" without re-running the reducer.
  • No new event types. No schema version bump. The proposal only changes WHEN the reducer runs and WHO surfaces its output; the reducer's contract is untouched.
  • Migrating to step() is mechanical: every existing append_event({"event_type": "step.started", ...}) becomes with step(...). One PR, one migration, one assertion in CI.

Cons

  • The lib/trace_log.step context manager is a new public API; existing callers using append_event directly must migrate for the metric to be reliable. The migration is mechanical and the CI gate enforces it, so this is an upfront cost paid once.
  • Threshold 0.95 is a starting value; legitimate async background tasks may sit below it. Out of scope for v1; documented as a follow-up with a per-subject exemption list keyed on subject_id prefix.
  • History file rotation at 200 lines is arbitrary. Configurable via subject_observability.history_max_lines in .dev-kit/state.json; default 200 is the right starting point for human-scale review (roughly one snapshot per workday × ~6 months).

Limitations

  • Measures ONE thing reliably: that every started subject terminates. Does not measure guard precision, recovery latency, learning delta, or any of the other 4 components. Those remain in the reducer's report for /dev-kit:evaluate; this proposal does not gate them.
  • The CI gate is binary: pass or fail at threshold. A project that wants monitoring without blocking can run bin/collect-effectiveness.sh --mode=ci --dry-run to surface the verdict as a check-run warning without exiting non-zero. --dry-run is one flag in the wrapper; not in v1.
  • The history file is per-worktree, not per-host. Cross-host aggregation is a follow-up; the data model (one JSON-per-snapshot, one history line per snapshot) is already shaped for upload.
  • Cannot auto-fix a producer regression. CI catches it; a human fixes it. The hand-off chain is the same as the umbrella's evidence-collection proposal but at a single, sharper metric.
  • The other 4 components of the reducer (prevention_quality, first_pass_quality, recovery_quality, measurement_integrity) remain observable via /dev-kit:harness-effectiveness and /dev-kit:evaluate for analysis. They are not gated.
