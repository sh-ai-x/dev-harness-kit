TL;DR

Linear 등록을 best-effort sync 에서 work 의 hard gate 로 전환.

현재 4 hook (PreToolUse Edit / SessionStart / UserPromptSubmit task-change / PostToolUse:Bash git worktree add) 은 전부 best-effort + owner-gated + silent skip. tools/linear_sync.py 1개가 진입점.

핵심 결정:

  • WorktreeCreate 시점에 Linear issue 존재를 강제 (없으면 자동 생성)
  • Project-scoped dedup — 동일 scope 의 기존 issue 가 있으면 link
  • Worktree-local canonical handle — .worktrees/<slug>/.dev-kit/linear.json 1개가 이후 모든 hook 의 단일 진실
  • 4 hook 전부 제거, WorktreeCreate 1개로 대체
  • PR merge → state: Done (기존 linear-pr-sync.yml 그대로 유지)

배경 — 동기

dev-harness-kit 는 plugin으로 여러 repo 에 설치되고, owner 가 한 repo 내에서 여러 worktree 를 동시에 운영한다. 현재 4 hook 의 결정적 약점:

  1. Race-free 시작 부재 — owner A 가 fix/foo worktree 를 2개 (X, Y) cut 하면 각 hook 이 자기 path 만 보고 issue 2개 생성. 중복 작업.
  2. 시점 모호 — Edit 발생 후에야 Linear 반영. plan/PRD 와 issue 가 매번 사후 sync.
  3. Edit-time noise — 5~30 edit / 1 PR = hook 5~30회 발화. commit log 가 issue 본문에 누적.

본 proposal 은 반응적 sync → 사전 강제 로 뒤집는다.

핵심 아이디어

worktree = 작업의 원자 단위. cut 시점에 Linear project 에 scope 가 등록되어 있어야 한다.

                                    ┌─ hit ──> link (no create)
WorktreeCreate ─> scope 추출 ─> Linear project 검색 ─┤

Race 방지 메커니즘

dev-harness-kit 가 1개 repo 의 N개 worktree 에 설치된 환경에서, owner 가 같은 scope 로 동시 cut 하는 시나리오:

시점Worktree X (owner)Worktree Y (owner)Linear
t0fix/foo cut 시작(대기)없음
t1scope fix/foo 검색 → miss(대기)없음
t2issue #123 생성 시도 (block)fix/foo cut 시작race
t3(200 OK 받음)scope fix/foo 검색 → hit (#123)#123
t4worktree 생성, handle ← #123worktree 생성, handle ← #123 (같은 ID)#123
t5작업 진행작업 진행 (또는 "이미 #123 처리 중" 알림으로 cancel)#123

핵심: Linear project 가 단일 source of truth. dedup 쿼리 (filter: { title: { eq: $scope } }) 가 항상 같은 결과를 본다. 단, t2→t3 사이에 두 번째 cut 도 같은 시점에 miss → create 시도 가능. 이 same-second race 는 별도 mitigation 필요 (limitations 참조).

비목표

  • Cross-repo dedup — dev-harness-kit 가 다른 repo 에 설치되어 있고 같은 scope 의 작업이 두 repo 에서 동시 진행되는 경우. 공유 dedup store (Redis/Lua) 필요. 본 proposal 의 v1 범위 외.
  • Linear API 변경 — webhook 인프라 도입. 현재 GraphQL 호출 그대로.
  • worktree GC / orphan issue 청소 — 별도 cron 작업.
  • non-git 환경 — git worktree 기반 워크플로우 전제.
  • 기존 `.dev-kit/hand-off/linear/main.json` 마이그레이션 — 1회성 migration script 는 rollout 단계에서 별도 PR.
  • multi-team / multi-project 환경 — 단일 Linear project 가정.

트레이드오프 (정직하게)

  1. false positive — investigation worktree 도 issue 생성됨 investigate/why-foo-fails 같은 브랜치도 Linear issue 가 생긴다. → 해결: branch pattern ^(investigate|research|spike)/ 은 tracking-only 모드로 강등 (issue body = "investigation, no implementation"). user 가 명시적으로 close 가능.
  1. scope 추출 실패 시 fallback — branch name 만으로 issue 제목을 만들면 noise (fix/typo → "Fix: typo"). branch 가 너무 generic 하면 user 에게 prompt 로 제목 받기. → 해결: _scope_from_branch() 가 12자 미만 / 동사만 있는 경우 LINEAR_REQUIRED=0 모드 + stderr 경고로 강등. v1 에서는 interactive prompt 미지원 (WorktreeCreate 는 server-side hook).
  1. network failure 시 worktree cut 자체가 block — Linear API down 이면 작업 시작 못함. 15s timeout 으로 빠지지만 그래도 fail-closed. → 해결: LINEAR_REQUIRED=0 env 또는 per-repo config 로 bypass 가능 (warning 만 출력). default 는 fail-closed.
  1. Edit-time hook 발화 0회 (성공 지표) — 검증 가능: tools/token_efficiency_analyzer.py 의 hook-call 카운트가 linear-* 패턴으로 0 이 되는지 측정 가능. (v1 proposal 의 "unverifiable" 지적은 정정함)
  1. 4 hook 사용자 워크플로우 breaking — release notes 에 breaking change 명시 + 1 release deprecation 경고.

성공 지표

  • 중복 작업 0건 (단일 owner 한정) — 동일 scope 의 동시 worktree cut 시 1개만 생성되고 나머지는 link. cross-repo dedup 은 v1 범위 외.
  • 100% worktree 가 Linear issue 를 가짐 — .worktrees/<slug>/.dev-kit/linear.json 존재율 (tools/dev_kit_status.py 로 측정)
  • Edit-time hook 발화 0회 — PreToolUse linear-* hook 제거 후 tools/token_efficiency_analyzer.py 의 hook-call 카운트 0
  • PR merge 시 state 자동 전이 100% — 기존 linear-pr-sync.yml 그대로

Before / After

Before (current state)

Today Linear auto-sync runs on 4 best-effort hooks that all delegate to tools/linear_sync.py::auto_sync. The triggers fire during work (PreToolUse Edit, SessionStart, UserPromptSubmit task-change, PostToolUse:Bash on git worktree add). Linear failures are non-blocking (per #539); the script always exits 0 and silently bails when the API key, worktree config, or owner-gate is missing. There is no enforcement that a tracking issue exists before work starts.

Evidence

  • hooks/linear-autosync.sh:1-9 declares PreToolUse Edit|Write|MultiEdit
  • hooks/linear-session-start.sh:2-9 declares SessionStart; owner-gated via auto_sync()
  • hooks/linear-task-change.sh:1-10 declares UserPromptSubmit; calls task_change_sync()
  • hooks/linear-worktree-create.sh:1-7 declares PostToolUse:Bash (NOT WorktreeCreate) — fires only when Claude Code runs the git worktree add command
  • tools/linear_sync.py:1645-1655 shows the entry-point dispatch: sync (default), auto-sync, task-change-sync, status, list, on, off, project-name, setup
  • tools/linear_sync.py:344-396 implements is_repo_owner() gate; non-owners bail silently from auto_sync()
  • Symptom: same owner cutting two worktrees on the same scope (fix/typo in both) registers TWO Linear issues, no dedup

After (proposed state)

Replace the 4 best-effort sync hooks with one WorktreeCreate hook that is mandatory (not best-effort), owner-gated, and project-scoped dedup-aware. The hook runs at the moment a new worktree is created — whether by Claude Code (worktree-auto-cut.sh) or by a manual git worktree add — and:

  1. Resolves the scope from branch + (optional) plan-id
  2. Searches the Linear project for an open issue with the same scope
  3. Links the existing issue (no create) OR creates a new one (block until 200 OK)
  4. Writes .worktrees/<slug>/.dev-kit/linear.json as the worktree's canonical Linear handle
  5. Stores issue ID in the worktree config so PR-merge can transition state to Done

All 4 current sync hooks are removed. The PR-merge state transition (tools/linear_pr_sync.py + .github/workflows/linear-pr-sync.yml) stays untouched.

Pros

  • Catches the same-owner-same-scope case the current 4-hook system misses (two worktrees cut by one owner on the same scope today produce two issues)
  • Reduces Edit-time hook fires from N-per-session to 1-per-worktree; token cost drops measurably on long sessions
  • Worktree = atomic unit of work; the worktree-local handle removes the "which session owns this issue" ambiguity
  • Owner-gate semantics preserved; non-owners still bail silently (no leak of contributor work into the owner's Linear workspace)
  • Existing PR-merge state transition is reused unchanged — no new CI surface

Cons

  • Network failure at worktree-cut time blocks the cut. Mitigation: LINEAR_REQUIRED=0 env var bypasses the gate with a warning; default is fail-closed (matches #539 "non-blocking" applies only to the in-session sync path)
  • WorktreeCreate fires for ALL git worktree add (not just Claude Code's). Mitigation: hook is scoped to dev-harness-kit installations via the existing config-presence check (linear-config.json:enabled); non-dhk worktrees are unaffected
  • Removes a feedback signal operators currently rely on (every-edit sync). Mitigation: PR-merge still publishes a state update; the Linear timeline remains complete for shipped work

Limitations

  • Linear's issueCreate GraphQL mutation has NO native unique-by-label enforcement. Dedup relies on a filter: { title: { eq: $scope } } query at hook time; same-second race between two cuts can still create two issues. Out of scope: optimistic concurrency on the Linear side. Mitigation: post-create label tagging + a one-shot reconcile cron
  • Branch-name-only scope detection fails for generic names (fix/typo, chore/cleanup). Out of scope: a plan-id discovery mechanism for users who don't run /dev-kit:plan first. Mitigation: hook prompts the user via stderr for a better title when scope extraction returns < 12 chars
  • Migration of existing .dev-kit/hand-off/linear/main.json to the per-worktree layout is deferred. Out of scope for this proposal. Mitigation: a follow-up one-shot migration script in the rollout PR
  • Cross-repo dedup (dev-harness-kit installed in N repos, same scope across two) is NOT supported. Out of scope: that scenario requires a shared dedup store (Redis/Lua). Documented as a future enhancement, not a v1 feature
