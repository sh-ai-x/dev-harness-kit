Decision and scope

Adopt a durable coordinator as the long-running owner of one PR lifecycle. A command invocation and GitHub webhook are both wake-up events into the same state machine. This proposal changes documentation only. The future implementation must preserve one-PR ownership, worktree isolation, bounded repair attempts, fail-closed verdict handling, and the existing human merge boundary.

Existing strengths retained by the improved workflow

The improved workflow is an extension of the current babysit-pr contract, not a replacement. The healthy path is shorter only because advanced reasoning is conditional; it still passes through the existing safety rails.

The new coordinator adds durable cursors, compact evidence packs, conditional RCA, and approval-ready waiting around these rails. It does not replace them with model confidence or an approval-distance score.

Durable and event-driven coordinator

Persist a coordinator record keyed by parent_pr with current_pr, attempt, head_sha, cursor, lease, context_epoch, approval_distance, failure_signature, frontier, hypotheses, and last_action. Persist every transition as an append-only event with event_id, provider event id, observed SHA, timestamp, actor, evidence references, model contract, and outcome. Materialized state is a deterministic projection of events; a restart replays from the last acknowledged cursor.

Wake sources are review submitted/edited/dismissed, check completed or workflow rerun, push, PR reopened/closed, lease expiry, scheduled reconciliation, and an explicit operator resume. Deduplicate provider retries by (provider, event_id) and work claims by (parent_pr, head_sha, context_epoch, failure_signature, action_class). A lease prevents two workers from mutating one PR; expiry creates a recovery event rather than silently taking over.

The coordinator waits on events, not an unbounded model turn. Reconciliation may poll only to repair a missing event or stale cursor, and every reconciliation result is recorded as an observed event.

Evidence frontier and RCA contract

The normal code-review path uses a compact evidence pack: current PR head SHA, changed files, one or more failing checks or review findings, the smallest useful log excerpt, reproduction output, and verification output. It is intentionally narrower than a full transcript. Each item has a stable evidence_id, observed SHA, freshness, and status (observed, reproduced, verified, or superseded).

RCA is activated only for a blocker that cannot be fixed from a direct test or review finding. It records one selected causal hypothesis, one expected signal, and one bounded intervention. After the action, the coordinator requires a new observation and classifies the result as fixed, changed, unchanged, regressed, or inconclusive. unchanged or inconclusive triggers escalation; it does not add another generic analysis phase to every PR.

Model capability contract

Models are replaceable workers behind a versioned contract. Before dispatch, the coordinator records provider, model, capability_version, context budget, tool permissions, and evaluator result. The worker must be able to: consume the compact frontier without inventing missing evidence; state one RCA hypothesis; reproduce before editing; make one bounded patch; run the required verification; emit structured evidence ids and exit codes; and stop with needs_human when policy, secrets, ownership, or contradictory evidence is encountered.

Capability levels are operational, not brand names: observe, reproduce, patch, verify, independent-review, and multi-step-recovery. A newer model may claim a higher level only after the replay/evaluation suite meets the relevant thresholds for evidence grounding, regression avoidance, structured-output validity, and abstention. Capability improvement changes worker selection and context compression, never the approval boundary or the meaning of a passing human review.

Context epochs and reanalysis

Increment context_epoch only when action-relevant state changes: the PR head SHA, a review finding, a check run/conclusion, a workflow definition, or a human decision. A cursor-only or duplicate event must not trigger model analysis. An epoch invalidates only evidence and plans tied to the changed blocker; unrelated review findings remain active.

Reanalysis is an escalation path, not a normal step. It is required before acting when the current compact evidence pack is stale, contradictory, or tied to an older SHA. The worker receives the new pack and the invalidated references, not the entire historical transcript.

Approval distance and human approval boundary

Approval distance is a typed vector, not a single optimistic score:

D = (required_checks, unresolved_findings, reproducibility, verification, independent_review, policy_exceptions, human_decision).

The coordinator may advance only when a component moves monotonically toward its terminal state: required checks become terminal-green, findings become resolved or explicitly dismissed, the root cause is reproduced, focused and full verification pass, independent review is recorded, policy exceptions are zero or explicitly escalated, and human decision is approved. A new SHA or finding can increase distance by reopening affected components. The approval packet contains the vector history, frontier, RCA ledger, diff/commit SHAs, command exit codes, and unresolved risks.

AI automation owns diagnosis, patching, local and CI verification, AI review/security checks, review-comment resolution, bounded repair PRs, and the final approval packet. Only the human reviewer with the required ownership context performs the final Approve and merge. The coordinator must refuse to interpret model output, missing verdicts, stale approvals, or approval_distance reaching zero as human authorization; gh pr merge remains outside the implementation.

AI-owned completion contract

The human should encounter a PR only after AI has completed every automatable activity. The hand-off packet must show: current head SHA, all required checks green, AI review and security verdicts, every finding resolved or explicitly escalated, focused and full verification evidence, changed-file summary, risk summary, rollback/recovery status, and the exact remaining human action: Approve and merge.

If any automatable gate is red, pending, stale, contradictory, or unexplained, the coordinator keeps working or enters a typed recovery state. It must not ask the human to perform ordinary diagnosis or testing. Human escalation is reserved for ownership, policy, secret handling, ambiguous product intent, unavailable external authority, or the final approval decision.

Code-review-optimized adoption plan

Adoption is optimized for the common code-review path: observe once, repair once, verify once, then wait for the next external event. Expensive RCA, context reset, and model routing are activated only on escalation.

Step 0 — Shadow measurement. Project current runs into compact evidence packs and approval-distance snapshots. Replay slow CI, force-push, duplicate event, worker crash, and human-review traces. Exit gate: deterministic, side-effect-free projection.

Step 1 — Durable resume. Persist the event cursor, lease, current SHA, blocker summary, last action, and approval packet while the existing repair actor remains unchanged. Exit gate: restart/retry safety and reconciliation for missed events.

Step 2 — Targeted repair gate. Route only changed checks or unresolved review findings to reproduce → one bounded fix → focused verification → push. Keep RCA/context epochs as escalation on stale, contradictory, or unchanged results. Exit gate: no duplicate push, no stale-evidence action, no regression in human gating.

Step 3 — Approval-ready wait. When checks are green and findings are resolved, produce the approval packet, request re-review at most once per SHA, and enter durable WAIT_FOR_APPROVAL. Exit gate: no code action is taken while only human approval is pending.

Step 4 — Event-first and capability evolution. Make GitHub events the primary wake source, retain reconciliation as a safety net, and evaluate newer models against replay traces. Exit gate: event replay equivalence, bounded recovery, and no safety regression.

Escalation lane (available from Step 2 onward): stale/contradictory evidence → context epoch refresh; unchanged result → one independent RCA; policy/secret/ownership issue → human recovery. These are not mandatory stages in the healthy path.

Rollback at every step: disable the newly enabled actor, preserve the append-only event log and approval packet, and resume from the last durable state. Rollback never converts a human-gate state into success.

Step transition and success gates

The coordinator must not advance because a timer elapsed or a model produced a plausible explanation. It advances only when the step's artifact and gate are present:

StepDurable artifactRequired gate
0replay reportdeterministic, side-effect-free projection
1cursor + lease + snapshotrestart, duplicate, and stale-lease recovery
2blocker evidence pack + verification recordone bounded, independently verified action
3approval packetchecks green, findings resolved, human decision pending
4event cursor + capability evaluation reportreplay equivalence and no safety regression

The terminal success remains APPROVED + required checks green. WAIT_FOR_APPROVAL is a healthy durable state, not a failure or a reason to manufacture an approval.

Tests and evaluation

Unit tests must cover deterministic frontier merging, hypothesis invalidation, monotonic distance transitions, epoch causes, capability gating, duplicate suppression, lease expiry, cursor replay, malformed verdicts, and bounded no-progress behavior. Scenario tests must replay: slow CI, ghost workflows, force-push during diagnosis, review dismissal followed by a new finding, worker crash after push, duplicate webhook delivery, provider outage, model downgrade, and restart between every transition.

Evaluation uses a fixed corpus of real-shaped traces plus synthetic adversarial traces. Required metrics are: zero automated merges; zero approvals from malformed/stale evidence; event replay equivalence; no lost or duplicated repair actions; time-to-human-approval; evidence-frontier precision; RCA reproduction rate; regression rate; abstention quality; token/cost per approval-distance reduction; and recovery time after worker/provider failure. Future models are compared on the same traces and must not regress safety metrics even when they improve speed or patch success.

Pros, cons, and open acceptance criteria

The design is attractive when a PR may wait hours or days for CI, reviews, provider recovery, or a human decision. It is intentionally conservative about convergence: progress means reduced, verified approval distance, not merely another model response or a changed comment.

Acceptance requires a documented state schema and migration rule, an event replay proof by test, a recovery procedure for missing events, a capability-evaluation report, a human-readable approval packet, and explicit evidence that runtime changes remain outside this proposal PR. Reviewers should reject the implementation if it weakens the human boundary, allows stale evidence to authorize action, or treats a stronger model as a substitute for verification.

Before / After

Before (current state)

babysit-pr already has evidence-oriented polling, a worktree lock, check-state caching, ghost-check classification, bounded repair attempts, and a human-only merge boundary. However, its operational contract is still expressed as a synchronous LOOP iter = 1 .. MAX_ITERS with sleep-based waiting. The durable coordinator document records a bounded attempt 0/1/2 lifecycle, but it does not define approval convergence as a measurable distance, an evidence frontier for RCA, model capability requirements, or context-epoch reanalysis when the world changes during a long run.

After (proposed state)

The proposed lifecycle is a durable, event-driven coordinator that can sleep between GitHub events without losing ownership, evidence, or causal history. Every wake-up advances an explicit approval-distance state machine. The coordinator maintains an evidence frontier and typed RCA hypotheses, invalidates stale conclusions when a new context epoch appears, and dispatches work only when the model capability contract is satisfied. It converges toward a human approval packet, never toward an automated merge.

Pros

  • Survives long waits and process restarts because event cursors, leases, epochs, evidence, and approval distance are durable rather than held in one model context.
  • Makes RCA falsifiable: each repair action must move the evidence frontier or be rejected as a duplicate/no-progress action.
  • Future model upgrades can improve diagnosis and patch quality behind a stable capability contract without changing approval semantics.
  • Preserves the existing human boundary: passing gates produce an auditable approval packet and never invoke gh pr merge.

Cons

  • A durable coordinator adds state-schema, replay, lease, and migration complexity; mitigation is an append-only event log plus deterministic projections and bounded state transitions.
  • Approval distance can be gamed by superficial progress such as a changed check without a causal fix; mitigation is typed evidence, reproduction, independent verification, and a no-regression guard.
  • More frequent reanalysis may spend tokens after benign events; mitigation is epoch-triggered invalidation, frontier deltas, and capability-aware escalation.
  • A stronger model may produce better patches but cannot remove ambiguity in policy or ownership; the approval boundary remains explicit.

Limitations

  • This PR does not implement the coordinator, change runtime behavior, or provision an event delivery service.
  • The design cannot guarantee GitHub event delivery; reconciliation polling or a manually resumed cursor is still required as a recovery path.
  • The model capability contract cannot prove semantic correctness; tests, independent review, and human approval remain required.
  • Approval distance is a decision aid, not a probability of merge or a permission to merge.
