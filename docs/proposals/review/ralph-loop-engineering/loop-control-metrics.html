Decision and priority

Decision: improve and control the loop, but stage the change. The highest-priority task is not a new retry heuristic. It is to make the existing state transition and the actual child attempt one durable, causally linked unit. Without that, every later metric is vulnerable to replay, missing output, or a false terminal state.

Priority order:

PriorityIssueWhy nowExit condition
P0RLE-00 stage/terminal contractThe real babysit adapter can stop at USER_MERGE_REQUIRED before SHIP, while docs/tests describe a three-stage chain.One explicit terminal owner is documented and stage metrics cannot hide a skipped SHIP.
P0RLE-01 durable checkpoint/resumeA restart can replay BUILD and the documented recovery path is not executable from RECOVERY_REQUIRED.Crash at every boundary resumes the next safe stage and never claims an unfinished attempt succeeded.
P0RLE-02 failure event journallast_action and raw stdout are not enough for forensics or aggregation.Every dispatch has a start/finish or interrupted event, with bounded evidence and a write-failure finding.
P1RLE-03 bounded Ralph controllerThe same-stage guard is dead in the production single-pass path.Controller chooses next work from checkpoint, enforces lease/deadline/budget, and classifies no-progress explicitly.
P1RLE-04 metric projection/reportThere is no Ralph-specific success, recovery, convergence, or evidence-coverage view.ralph_drive.sh metrics returns reproducible JSON and a human report from events only.
P2RLE-05 closed-loop improvementA metric without a safe experiment loop only creates dashboards.Shadow policy comparison and a separate accepted proposal show an improvement without safety regression.

The first implementation PR should land RLE-01 and RLE-02 together, after RLE-00's terminal ownership is made explicit. A checkpoint without an attempt journal can resume from a misleading state, while a journal without checkpoint ordering cannot control execution. RLE-00 must not be “fixed” by blindly forcing SHIP: whether BABYSIT or SHIP owns the human-merge boundary is a contract decision that the implementation and docs must agree on.

Proposed control-plane architecture

user gates + attended_lock
           │
           ▼
Ralph Controller ── lease / deadline / attempt budget ──┐
    │                                                   │
    ├─ checkpoint snapshot (.dev-kit/ralph/<session>.json)
    ├─ lifecycle event adapter ── trace/events.jsonl     │
    └─ derived progress + metrics                       │
                                                        ▼
    BUILD (execute output + events)
        → BABYSIT (babysit-state + check/review evidence)
        → SHIP (review/tag/merge boundary)
                                                        │
             reducer: metrics + recovery decision ◄────┘

The controller is the only component allowed to advance Ralph's sub-stage. Child skills retain authority over their internal loops:

  • BUILD reports step-level output and the existing self-fix guard; Ralph does not infer a green build from a zero exit code without the child artifact reference.
  • BABYSIT reports its durable state, failure signature, no-information count, wake time, and terminal/recovery reason; Ralph does not reset its context or silently turn MISSING review evidence into approval.
  • SHIP remains the final policy boundary. USER_MERGE_REQUIRED is an expected terminal outcome, not a failure and not a merge command.

A run has one stable run_id; every stage execution has a unique attempt_id; retries and recovery re-entry keep the run id but receive a new attempt id. The pair is the join key for state, events, artifacts, and metrics.

Nested loop events carry parent_run_id and parent_attempt_id. A child loop's iteration is not a Ralph stage attempt, and a Ralph retry must not reset the child's own state. This prevents double-counting and avoids stacking MAX_ITERS on top of another hidden cap. Standalone invocations can continue using their current logs; Phase 1 only promises complete registry coverage for loops reached from an active Ralph run.

The controller must show a loop graph in the report: parent Ralph run → stage attempt → child loop → child attempt → artifact/check/review evidence. A missing child edge is an observability finding, not a successful no-op.

State, event, and failure contracts

Checkpoint contract

Additive fields in the Ralph state snapshot:

{
  "schema_version": 2,
  "run_id": "ralph-<opaque-id>",
  "checkpoint_seq": 17,
  "current_stage": "ATTENDED_RUN",
  "sub_stage": "BABYSIT",
  "last_completed_sub_stage": "BUILD",
  "active_attempt": {
    "attempt_id": "attempt-17",
    "stage": "BABYSIT",
    "started_event_id": "evt-start-17",
    "lease_owner": "<worker-id>",
    "deadline": "<ISO-8601>"
  },
  "terminal_reason": "",
  "recovery_reason": "",
  "next_action": "resume BABYSIT attempt-18"
}

State transitions are ordered as: durable attempt.started event → child dispatch → durable attempt.finished or attempt.interrupted event → atomic checkpoint snapshot. On restart, an active attempt with no finish event is never treated as success. The reconciler marks it interrupted, checks child state/artifacts, and either resumes from the last verified boundary or lands in RECOVERY_REQUIRED.

The load path validates schema, enum, counters, path containment, and lease ownership. A corrupt snapshot is not silently replaced by a new run; replay from valid events is attempted, and failure becomes an explicit checkpoint_corrupt recovery finding.

Event contract

Keep the existing trace_log v1 required fields and add Ralph-specific fields additively:

FieldContract
run_id, attempt_id, event_idNon-empty stable ids; duplicate writes are idempotent.
stage, sub_stage, event_type, outcomeControlled values; child-specific details go in evidence_ref.
parent_id, checkpoint_seqCausal link and monotonic run order.
started_at, ended_at, duration_msUTC timestamps and measured wall duration; absent means unknown, not zero.

git_sha, branch, pr_numberContext only; never proof that a push or merge happened.

Minimum event types are run.started, stage.attempt.started, stage.attempt.finished, stage.attempt.interrupted, guard.blocked, guard.allowed, retry.scheduled, recovery.required, observability.degraded, terminal.reached, and run.closed.

Failure classes include child_exit, child_timeout, child_exception, no_progress, watchdog_limit, stale_lease, checkpoint_corrupt, event_write_failed, audit_evidence_missing, worktree_policy, cleanup_target_rejected, human_merge_boundary, and unknown. A failure class is a label for analysis; the raw bounded evidence and artifact refs remain the source for diagnosis.

Log safety

Event writes are append-only, locked, flushed/fsynced for checkpoint events, and deduplicated by event id. Payloads must not contain secrets, tokens, full prompts, or unlimited child output. Paths are resolved and checked under the run artifact root before writing; an unresolved cleanup target is rejected and logged. A write failure never becomes a green metric. If the failure itself cannot be logged, the process exits with a distinct observability/environment code and leaves the last valid checkpoint intact.

Loop-control policy

The controller uses this decision order on every wake or invocation:

  1. Load and validate the snapshot; acquire the session lease. A live lease blocks a second worker. A stale lease emits stale_lease and requires bounded recovery instead of concurrent dispatch.
  2. Replay the event tail from checkpoint_seq. Close any attempt that has a finish event; mark an open attempt interrupted. Never infer completion from a timestamp, process exit, or Markdown line.
  3. Choose the next work from the last verified child evidence. BUILD resumes from execute's step output/index; BABYSIT resumes from .dev-kit/babysit-state.json; SHIP is eligible only after the authoritative review/tag preconditions are present.
  4. Check the run deadline, per-stage attempt budget, and inherited child safety state. If a limit fires, emit the limit event and land in RECOVERY_REQUIRED with a resumable next action.
  5. Emit stage.attempt.started, dispatch exactly once for the attempt id, capture real stdout/stderr/exit/duration, and emit a terminal attempt event. A retry is allowed only if the classifier says the child outcome is resumable and the operation is idempotent.
  6. Compute a progress fingerprint from stage, child head/check state, artifact hashes, failure signature, and verification result. Same fingerprint without evidence change increments no-progress; a changed failure with stronger verification is progress. Two Ralph re-entries without progress are a recovery signal, while child policies remain authoritative for their own three-cycle/three-poll limits.
  7. Write the checkpoint after the event, release the lease, and return a terminal or wake result. Backoff is bounded and stored as next_wake_at; no busy loop is allowed.

This makes the loop a state machine with explicit ownership rather than a for sub in SUB_STAGE_ORDER traversal. It also makes “resume” a deterministic operation: it means resume the next unverified attempt, not repeat every child skill.

Metric contract and initial targets

Metrics are pure reductions over valid events and referenced child evidence. Every value includes numerator, denominator, coverage, dimensions, and evidence event ids. A missing denominator is null with INSUFFICIENT_EVIDENCE, never 0% and never 100%.

Required dimensions are skill, stage, sub_stage, outcome, failure_class, mode (legacy/shadow/controlled), provider, model, git_sha, and repo. Provider/model are empty when not recorded; the reducer must not silently attribute identity.

Initial rollout gates are deliberately small and evidence-oriented:

  • Do not enable controlled mode unless synthetic crash/restart tests achieve resume_success_rate >= 0.95 and evidence_completeness >= 0.99.
  • Treat any cleanup policy violation, attended-lock bypass, auto-merge, or audit-MISSING-to-approval conversion as a release blocker even if terminal rate improves.
  • Collect a baseline of at least 30 runs or 14 days before setting product thresholds for terminal rate, p95 latency, retries, or cost.
  • Do not add token/cost optimization to the primary score until event coverage is stable; otherwise the system may reward under-logging.

Rollout, verification, and rollback

Phase 0 — observe only

Add the event adapter and pure reducer. Wrap existing Ralph dispatches without changing stage order or retries. Compare projected metrics with current state/child outcomes. Acceptance: no workflow exit-code change, no prompt/merge-policy change, and 100% of synthetic events have stable parent links.

Phase 1 — durable checkpoint

Add schema validation, checkpoint sequence, active-attempt recovery, lease, and resume. Keep the legacy traversal as a feature-flagged fallback. Acceptance: kill the process before and after each of BUILD/BABYSIT/SHIP dispatch; recovery never duplicates a verified terminal side effect and never reports an open attempt as success.

Phase 2 — controlled loop

Enable progress fingerprints, stored backoff, stage/deadline budgets, and explicit retry classification for resumable child results. Existing child guard limits remain unchanged. Acceptance: no busy loop, bounded attempts, stale worker cannot dispatch, and rollback to legacy mode is one environment/config change.

Phase 3 — operational report

Add ralph_drive.sh events and metrics, derived progress rendering, and the metric coverage/release gates. Acceptance: reports are reproducible from a copied event journal and show insufficient evidence for truncated/missing records.

Phase 4 — improvement experiments

Use shadow policy comparisons to test one change at a time (for example, backoff or diagnosis strategy). Any metric-driven policy change gets a separate proposal, explicit safety thresholds, and a rollback. No self-modifying or LLM-only control policy is included here.

Verification commands for the implementation PR should include the focused Ralph/event/metric suites, existing executor and babysit suites, git diff --check, hook/worktree policy checks, and one end-to-end noop run with a captured event journal. The PR must quote actual exit codes, test counts, and metric coverage rather than a prose “all green”.

Issue plan and acceptance checklist

Proposed GitHub issues after this proposal is accepted:

  1. RLE-00 — Align stage and terminal ownership (P0). Reproduce with a successful real dispatch and assert whether SHIP runs before USER_MERGE_REQUIRED; update the public contract, state transition, and metrics so a skipped stage is explicit and intentional.
  2. RLE-01 — Make Ralph checkpoint resume real (P0). Reproduce by persisting sub_stage=BABYSIT, restarting, and asserting BUILD is not dispatched. Add crash-boundary and schema-corruption tests.
  3. RLE-02 — Add Ralph lifecycle/failure evidence (P0). Reproduce by forcing timeout/exception/audit-MISSING and inspecting event ids, refs, redaction, and interrupted-attempt recovery.
  4. RLE-03 — Activate bounded controller semantics (P1). Reproduce a changed and unchanged failure fingerprint; assert progress advances, no-progress backs off, and limits land in recovery.
  5. RLE-04 — Add Ralph metric projection and CLI (P1). Reproduce from a fixture journal; assert formulas, dimensions, coverage, and expected USER_MERGE_REQUIRED handling.
  6. RLE-05 — Run shadow improvement experiment (P2). Reproduce a legacy-vs-controlled comparison; accept only if reliability and safety metrics do not regress. This issue must not mutate production control policy by itself.

Definition of done for the first two issues:

  • [ ] A single run_id joins state, attempt events, child artifacts, progress, and metrics.
  • [ ] A process kill at every stage boundary produces an explicit interrupted/recovery record and a deterministic next action.
  • [ ] No event or metric treats missing audit/review evidence as green.
  • [ ] Logs are bounded, redacted, append-only, idempotent, and safe under invalid/symlinked/broad cleanup paths.
  • [ ] Existing attended_lock, worktree isolation, review, and human merge tests remain green.
  • [ ] Legacy mode remains available until the baseline and rollback review are complete.

Ambiguities (open questions)

  1. A1blocking
    Which existing event store is canonical for Ralph lifecycle events: trace_log, effectiveness_collection, or a new journal?
    Default: trace_log v1 is the canonical trajectory event source because executor events already use its parent-link contract; Ralph metrics are a separate pure projection. Reuse effectiveness_collection's fsync/hash-chain patterns where trace_log is hardened, without creating a third store.
  2. A2blocking
    What happens when a safety-critical event cannot be persisted?
    Default: Fail closed for checkpoint-critical transitions: persist RECOVERY_REQUIRED with an observability-degraded reason if possible and do not claim success. Best-effort output snippets may be omitted only when the event still records the omission.
  3. A3default
    Should Ralph add retries on top of build and babysit-pr retries?
    Default: Do not duplicate child retry policy. Ralph owns stage-attempt budgets, deadline, backoff, and resume; build owns MUST-37 and babysit-pr owns no-progress/MAX_ITERS. Ralph retries only when the child outcome is explicitly resumable and idempotent.
  4. A4default
    How should CI or LLM audit MISSING affect a run metric?
    Default: Classify it as audit_evidence_missing / insufficient evidence, never as approval and never as an ordinary code failure. The run may remain resumable, but terminal quality metrics exclude it until an authoritative verdict exists.
  5. A5default
    When should metric thresholds become automatic control inputs?
    Default: Never in the first rollout. Collect a two-week or 30-run baseline, review distributions, then propose thresholds in a separate accepted change with shadow comparison and rollback.

Scope

In scope

  • A single canonical Ralph run identity and versioned checkpoint/attempt model under .dev-kit/ralph/.
  • Resume-aware BUILD → BABYSIT → SHIP orchestration after process crash, child timeout, RECOVERY_REQUIRED, or stale lease.
  • Append-only structured lifecycle, guard, recovery, and terminal events with bounded redacted logs and artifact references.
  • Derived ralph_progress.md output and a local JSON/Markdown metrics CLI.
  • Pure metric projection with reliability, convergence, efficiency, safety, observability, and evidence-completeness dimensions.
  • Synthetic crash/restart, duplicate-event, timeout, stale-lock, audit-MISSING, cleanup-safety, and regression tests.
  • Shadow-mode rollout and explicit rollback to the legacy single-pass controller.

Out of scope

  • Auto-merge, force-push, review bypass, or changing the human merge boundary.
  • Replacing build's per-step executor, MUST-37 self-fix, babysit-pr's repair strategy, or ship's authoritative review/tag checks.
  • A hosted observability service, external database, background daemon, or multi-repository coordinator.
  • LLM-generated metric interpretation being allowed to mutate policy without deterministic guard evaluation.
  • Retroactively claiming success for runs that have no durable terminal evidence.
  • Editing unrelated PR implementation work or changing hook manifests unless a later accepted issue explicitly proves it is required.

Before / After

Before (current state)

Ralph has a useful attended-lock state machine and delegates the actual work to build, babysit-pr, and ship. The control loop is not yet a durable execution loop, however. The persisted top-level state, child skill state, stdout, failure logs, and effectiveness reports are separate surfaces. A restart can therefore replay work from the beginning, lose the causal relationship between an attempt and its failure, or report a terminal-looking state without enough evidence to measure it.

The project already contains the ingredients for a safe design: build writes real step output and evidence events, trace_log has a validated append-only event contract, effectiveness_collection has bounded append+fsync storage, and babysit-pr has a resumable state machine. This proposal connects those pieces instead of introducing another competing loop or another unstructured progress file.

Evidence

  • skills/ralph/lib/ralph_chain.py:385-415 iterates BUILD → BABYSIT → SHIP from the beginning and saves only the current sub_stage before dispatch; it does not select the next work from a recovered checkpoint.
  • skills/ralph/lib/ralph_chain.py:454-460 stores only child stdout in build_state, babysit_state, and ship_state; exit code, stderr, duration, attempt identity, and evidence references are not durable Ralph fields.
  • skills/ralph/lib/ralph_chain.py:557-573 rejects every loaded state whose current_stage is not ATTENDED_RUN, so the documented re-invocation path cannot itself resume RECOVERY_REQUIRED.
  • skills/ralph/scripts/ralph_drive.sh:73-236 exposes init/status/can-ask/advance/rewind/run-attended, but has no resume, event, failure-log, or metric command.
  • skills/ralph/templates/ralph_progress.md:1-7 describes a per-run log, but no runtime writer creates or appends that file.
  • tests/test_ralph_chain.py:214-241 reaches same-stage-repeat only by monkey-patching SUB_STAGE_ORDER; the production runner is explicitly a single pass.
  • tests/test_ralph_chain.py:249-267 accepts any BUILD/BABYSIT/SHIP sub_stage after reload, so it does not prove crash/restart resume semantics.
  • skills/ralph/lib/ralph_chain.py:234-250 maps a successful BABYSIT dispatch directly to USER_MERGE_REQUIRED, while the public contract describes BUILD → BABYSIT → SHIP; the SHIP stage is therefore skipped on the real happy path.
  • lib/execute.py:807-838 already writes real exit_code/stdout/stderr/duration_seconds output, and lib/execute.py:926-949 emits causal verification events; Ralph currently captures neither contract as a structured attempt.
  • lib/trace_log.py:278-326 provides event validation, locking, dedupe, and parent links; lib/effectiveness_collection.py:609-678 provides append+fsync and hash-chain durability, but neither is wired to Ralph stage lifecycle.
  • lib/babysit_pr_loop.py:177-220 has a useful three-outcome no-information policy, yet Ralph does not consume its iteration, failure signature, wake, or recovery evidence as metrics.
  • The wider skill set has independent loop owners: research Phase 0-3 escalation (skills/research/SKILL.md:33-53), plan's 5-gate and loop-log (skills/plan/SKILL.md:305-324,431-445), build step/self-fix (skills/build/SKILL.md:106-115), build-debug 4 phases (skills/build-debug/SKILL.md:55-84), build-refactor 4 passes (skills/build-refactor/SKILL.md:48-55), TDD Red-Green-Refactor (skills/build-tdd/SKILL.md:24-32), build-verify fail-back (skills/build-verify/SKILL.md:61-63), local babysit (skills/babysit-pr-local/SKILL.md:144-166,255-266), and CI-triage process (skills/ci-triage/SKILL.md:50-57,108-113).

After (proposed state)

Ralph becomes a bounded, resumable controller with three explicit planes:

  1. Control plane — a versioned checkpoint plus lease/attempt record chooses the next sub-stage from committed evidence, not from a fixed list. A process crash, stale worker, child timeout, or RECOVERY_REQUIRED state is represented as an interrupted attempt and can be resumed safely.
  2. Evidence plane — every stage emits validated start, finish, retry, guard, recovery, and terminal events with an attempt id and artifact references. The operator-readable ralph_progress.md is derived from this journal; it is never the source of truth.
  3. Measurement plane — a pure projection computes Ralph-specific reliability, convergence, efficiency, safety, and evidence-completeness metrics. Missing or degraded telemetry is reported as insufficient evidence and never converted into success.

The first rollout runs in shadow/metrics-only mode, then enables durable resume, then enables controller retries. Existing build MUST-37, babysit-pr no-progress/MAX_ITERS, attended_lock, review gates, human merge boundary, worktree guard, and fail-closed audit semantics remain authoritative. Metrics do not approve code and do not authorize merge.

Pros

  • Fixes the highest-risk correctness gap first: a killed or restarted Ralph run can identify the last durable attempt and resume the correct stage without replaying completed work.
  • Makes every failure inspectable: exit code, stderr reference, duration, failure class, child state, and event ids are queryable instead of hidden in one truncated last_action string.
  • Uses current project primitives (trace_log, harness_effectiveness, effectiveness_collection, executor output, and babysit state) so the metric contract has real evidence and does not create a third unrelated telemetry system.
  • Separates expected human merge from recovery, audit MISSING from approval, and observability degradation from workflow success. This prevents the CI/audit ambiguity seen during PR #849 from becoming a false green.
  • Makes loop improvement measurable before enabling autonomous policy changes: baseline first, then shadow metrics, then bounded controller changes with rollback.
  • Preserves existing safety boundaries: no auto-merge, no force-push, no Ask after attended_lock, no bypass of per-step worktrees, and no silent retry beyond a budget.

Cons

  • The repository will temporarily have both legacy state snapshots and the new event projection. Mitigation: define one-way compatibility readers, make the event journal canonical for new runs, and remove only redundant legacy fields after a migration period.
  • A durable event write adds a small amount of I/O at every stage boundary. Mitigation: emit compact metadata plus artifact references, cap payloads, batch only non-safety metrics, and retain fsync for checkpoint-critical events.
  • Metric names and thresholds can create perverse optimization. Mitigation: publish numerator, denominator, coverage, and evidence ids; never score missing data as zero or success; keep learning/auto-policy changes disabled until a baseline exists.
  • Resuming a child process is not always safe after an external side effect. Mitigation: reconcile open attempts as interrupted, require idempotency keys for dispatch, and resume at the last verified boundary; never infer a successful push or merge from process death.
  • Cross-skill integration expands the test surface. Mitigation: land the event adapter and pure reducer separately from controller activation, and retain a legacy mode behind a feature flag during rollout.

Limitations

  • No metric can prove the semantic quality of an LLM change from exit code alone. Independent checks and review evidence remain required; self-reported child success is labeled as such.
  • The controller cannot safely replay an arbitrary external command that was interrupted after side effects. It can classify and surface the ambiguity, not undo the side effect.
  • The first version measures Ralph runs within one repository and one session namespace. Distributed multi-repository coordination, hosted dashboards, and cross-machine leases are out of scope.
  • The proposal does not change the meaning of build's three-cycle guard, babysit-pr's no-progress/MAX_ITERS policy, or the human merge requirement. It measures and coordinates those policies; it does not replace them.
  • Historical runs lack the new event fields. Historical metrics are partial and must be shown with insufficient coverage rather than backfilled from prose or stdout.
