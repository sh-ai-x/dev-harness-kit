Problem

The root agents/ directory now holds the repo's project-specific subagent definitions. Every custom agent available in this repo today — backend-architect, frontend-developer, database-admin, devops-troubleshooter, knowledge-manager — is a global persona for web-app domains, none of which match what this repo actually does (author skills, hooks, and CLAUDE.md for a Claude Code / Codex harness).

This proposal answers three questions in order: (1) what test decides whether a task deserves a dedicated subagent at all, (2) which candidates survive that test against real evidence from this repo's own session logs, and (3) what the hand-off contract between the orchestrator and any subagent should look like.

Decision gate

A candidate only earns a project agent file if it clears all three checks below, in order. The first two encode "don't build a subagent when a skill or a single Task call already solves it" — the same discipline Anthropic states directly: "optimizing single LLM calls... is usually enough," and agentic complexity is justified only when the simpler approach demonstrably underperforms [src:https://www.anthropic.com/engineering/building-effective-agents;ts:2026-07-30;type:primary].

1. Is this solvable by a skill or a deterministic script?
     yes -> reject, use the skill
2. Does it need judgment applied to N independent targets,
   in parallel, not just one?
     N = 1 -> reject, a plain Task call is enough
3. Is there corpus evidence from logs/claude-code/*.jsonl,
   not just a plausible-sounding argument?
     no evidence -> reject until evidenced
all three pass -> build it

Anthropic's own bar for when orchestrator-workers beats a single pass — "subtasks cannot be pre-defined," i.e. the decomposition itself needs judgment [src:https://www.anthropic.com/engineering/building-effective-agents;ts:2026-07-30;type:primary] — is check 2 above, restated for this repo.

Recommended build — worktree-janitor

name: worktree-janitor
description: |
  PROACTIVELY audits .worktrees/* against merged/closed branches and
  uncommitted state. Reports removal candidates — never deletes.
tools: Read, Grep, Bash   # git/gh read-only; no Write/Edit
model: sonnet

Dispatch envelope (composed per batch of worktrees, fanned out in parallel — one dispatch per batch, not per worktree, to keep the (N+1)x Supervisor-pattern cost bounded):

FieldValue
goalClassify these worktrees as safe-to-remove / needs-human-check, with a one-line reason each
scopethe assigned worktree paths only; read-only — no git worktree remove
contextorchestrator already knows: N tracked worktrees total, and which ones the analyzer pre-classified merged/gone
budgetmax 3 tool-calls per worktree (status check + branch-merge check + optional log tail)
moderead-only

Report envelope: status (success/partial/failed), evidence (quoted git/gh output, capped near 1,000-2,000 tokens per the isolation mechanism Anthropic measured — a subagent explores extensively internally but returns only a condensed summary [src:https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents;ts:2026-07-30;type:primary]), changed (always [] — read-only), and next_actions — a list, one entry per worktree in the batch (plural so a mixed-batch result is representable in one report — PR #494 review R1). Each entry is either the exact git worktree remove <path> command for a human to run, or "needs check: <reason>".

Orchestration flow

Star topology only — orchestrator to each subagent, never subagent to subagent. This is the Supervisor + Fan-Out shape from the 2026 pattern survey, chosen specifically because it has "the widest native framework support... and the best-understood failure modes" [src:https://www.digitalapplied.com/blog/multi-agent-orchestration-5-patterns-that-work;ts:2026-07-30;type:secondary], and because the star shape structurally avoids the loop-style failures (arbitration loops, coordination thrashing) that Debate and Swarm patterns need explicit guards against.

1. Orchestrator partitions the worktree set into K batches.
2. All K dispatch envelopes are issued in ONE message
   (true parallelism — sequential Agent calls would serialize).
3. Orchestrator's turn ends / continues other work. No polling.
4. Each worktree-janitor instance runs its own tool calls,
   isolated context, and emits a report envelope on stop.
5. The harness fires one task-notification event per stop.
   When several land close together, batch them chronologically.
6. Orchestrator merges the K reports into one removal-candidate
   list and presents it to the human.
7. The agent never runs `git worktree remove` itself — every
   report's `next_actions` entries are commands for a human to run.

Explicitly not building

  • Swarm (peer agents, shared memory, dynamic spawning) — no task in this repo needs agent-to-agent coordination rather than orchestrator-to-agent; adopting it imports "coordination thrashing" risk for zero measured benefit.
  • Debate (same prompt to N agents, judge arbitrates) — useful when ~2.5x cost buys multi-perspective validation; this repo's /dev-kit:review fan-out (parallel per-dimension experts plus a verifier pass) already covers that need without a generic Debate primitive.
  • Phase-based personas (a generic ASK / BUILD / REFINE roster) — considered and rejected: this repo's Plan -> Build -> Review -> Ship skill pipeline, backed by hooks (tdd-guard, stop-verify), already deterministically enforces that same three-stage discipline. A phase-based subagent roster would duplicate it while losing the domain judgment (skill-authoring.md's L6/L7 gate, worktree merge heuristics) that made worktree-janitor pass the decision gate above.
  • `skill-auditor`, `session-cost-reviewer` — rejected per the candidates table; recorded here so they are not re-proposed without new corpus evidence.
  • Memory-management / audit-management subagent — proposed during design discussion as "a subagent to manage context effectively." Fails check 2 structurally, not for lack of a real pain point: managing context within one ongoing session is a single-target task (there is only one conversation to compact), so there is nothing to fan out across, and a subagent's entire value proposition here — parallel, isolated, async hand-off — does not apply. The closest real evidence, HEAVY_CONTEXT firing on 127/167 sessions, points at the orchestrator not following session-hygiene.md rule 2 ("cartography, not re-reads") closely enough — a process fix, not something a spawned agent can parallelize its way out of. Reframed as a batch audit across many past sessions it would clear check 2, but then fails check 1: /dev-kit:token-analyzer already is that skill.

Follow-up idea — context hygiene as a hook, not a subagent

If the underlying concern (127/167 sessions hitting HEAVY_CONTEXT) is worth acting on proactively rather than only in /dev-kit:token-analyzer's after-the-fact report, the shape that fits this repo's existing conventions is a hook, not an agent — session-hygiene.md rule 4 already prescribes "spawn a sub-agent for noisy exploration," but the detection itself is deterministic (the same rule token_efficiency_analyzer.py already encodes), which is exactly what a hook should own instead of an LLM judgment call.

Sketch, mirroring the existing session-start-check.sh gentle-nudge pattern (never blocks, only informs):

  • Trigger: a turn-count / tool-call-count threshold, or a PreCompact hook, firing the same HEAVY_CONTEXT check tools/token_efficiency_analyzer.py already runs post-hoc.
  • Action: emit an additionalContext nudge pointing at the specific large-file re-read or repeated-message pattern detected — not a generic "context is large" warning.
  • Why a hook, not a subagent: no N to parallelize across; the check is deterministic; this is check 1 of the decision gate (skill/script-solvable) failing the same way skill-auditor did, just for a different reason.

Status: idea only. Needs its own scoping pass (exact threshold, false-positive rate against real sessions) before it earns a place in hooks/ — not bundled into this proposal's "Next steps" so worktree-janitor isn't blocked on it.
