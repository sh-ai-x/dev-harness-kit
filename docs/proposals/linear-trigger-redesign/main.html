TL;DR

Linear 등록은 best-effort sync가 아니라 work의 hard gate여야 한다.

현재 4개 hook (linear-autosync / linear-prompt-sync / linear-worktree-create / linear-session-start) 은 전부 반응적 — edit/세션/작업트리 생성 후에 Linear에 반영. 결과:

  1. deduplication 안 됨 — 같은 dev-harness-kit 가 설치된 다른 저장소에서 동일 작업을 시작해도 서로 모름
  2. 시점 모호 — 이슈가 commit 5개 후에야 생기거나, 안 생기거나
  3. 노이즈/시그널 비율 불리 — edit 단위 trigger는 정보 중복

핵심 결정:

  • WorktreeCreate 시점에 Linear issue 존재를 강제 (없으면 자동 생성)
  • Project-scoped dedup — 동일 scope (브랜치/PR 제목 후보) 의 기존 issue 가 있으면 새로 만들지 않고 link
  • Worktree-local canonical handle — .worktrees/<slug>/.dev-kit/linear.json 1개가 이후 모든 hook 의 단일 진실
  • PreToolUse / UserPromptSubmit 기반 sync hook 전부 제거
  • PR merge → state: Done (기존 linear-pr-sync.yml 그대로 유지)

배경 — 왜 sync 모델이 실패하는가

dev-harness-kit 는 plugin으로 다른 저장소에 설치된다. 같은 hook 시퀀스가 저장소 A, B, C 에서 동시에 돌아간다. 현재 sync 모델은 두 가지를 보장 못 함:

  1. Race-free 시작 — User A (저장소 X) 가 fix/linear-autosync 작업을 시작해도, User B (저장소 Y) 가 같은 작업을 시작해도 둘 다 자기 hook만 보고 자기 Linear issue 만 만든다. 중복 작업 발생.
  2. Issue 가 work 보다 먼저 존재 — dev-harness-kit 의 다른 워크플로우 (/dev-kit:plan, /dev-kit:proposal, /dev-kit:build) 가 만든 산출물과 Linear issue 가 매번 사후 동기화. 본문 commit log 로 채워짐.

본 proposal 은 Linear 등록을 사후 반영 에서 사전 강제 로 뒤집는다.

핵심 아이디어 (한 문장)

worktree = 작업의 원자 단위. worktree 가 cut 되기 전에 Linear project 에 scope 가 등록되어 있어야 한다.

Hook 시퀀스 (before / after)

Before (현재 — 4 hook, 다 best-effort):

UserPromptSubmit ─┐
WorktreeCreate ───┤
SessionStart ─────┼──> linear_sync.py ──> Linear (있으면 update, 없으면 create)
PreToolUse Edit ──┘                            (silent skip if no key)

After (제안 — 1 hook, hard gate):

                                    ┌─ hit ──> link (no create)
WorktreeCreate ─> scope 추출 ─> Linear project 검색 ─┤
                                    └─ miss ─> create (block until 200 OK)
                                      │
                                      ▼
                              .worktrees/<slug>/.dev-kit/linear.json
                                      │
                                      ▼
                            (work proceeds; all hooks READ this file)

종료는 기존 linear-pr-sync.yml 이 PR merge 시 state: Done 으로 전이. 그 외 별도 hook 없음.

Race condition 방지 (왜 이게 해결책인가)

dev-harness-kit 가 N개 저장소에 설치된 환경에서, 두 사용자가 같은 scope 로 동시에 worktree 를 cut 하는 시나리오:

시점User A (저장소 X)User B (저장소 Y)Linear 상태
t0fix/foo worktree cut 시작(대기)없음
t1scope fix/foo 검색 → miss(대기)없음
t2issue #123 생성 시도 (block)fix/foo worktree cut 시작race
t3(200 OK 받음)scope fix/foo 검색 → hit (#123)#123
t4worktree 생성, .dev-kit/linear.json ← #123worktree 생성, .dev-kit/linear.json ← #123 (같은 ID)#123
t5작업 진행작업 진행 (또는 "이미 #123 처리 중" 안내로 cancel)#123

핵심: Linear project 가 단일 source of truth — tools/linear_sync.py:_find_or_create_project() 가 이미 같은 이름의 project 를 보장하므로, dedup 쿼리 (scope eq) 가 항상 같은 결과를 본다. 마지막 create 만 mutex 가 필요 — project_id + scope 를 unique key 로 두고 409 conflict 시 재조회.

옵션장점단점채택
A. 현행 유지 (4 hook sync)변경 없음race 가능, 노이즈, dedup 없음❌
B. Pre-push hook onlyshipping 시점 단일 sync진행 중 가시성 0, mid-work push 누락❌
C. Post-commit hook의도 단위 (commit)auto-fix loop 충돌, WIP 노이즈, squash 손실❌
D. Plan-gated (plan 승인 시)명시적, intent 캡처worktree 가 plan 보다 먼저 생기는 경우 누락△ 보완
E. WorktreeCreate gate + deduprace-free, work 가 issue 보다 늦게 생성, worktree=unitscope 추출 정확도 의존, plan-less 작업은 branch name 으로 대체✅

권장안은 E (메인) + D (보완). WorktreeCreate 시 plan-id 가 .dev-kit/plan-id 로 박혀있으면 (이미 /dev-kit:plan 가 저장) 그 plan 의 PRD 요약을 issue body 로 사용. 없으면 branch + worktree context 에서 scope 추출.

비목표 (Out of scope)

  • Linear API 자체 변경 / webhook 인프라 도입 (현재 GraphQL 호출 그대로)
  • worktree GC / orphan issue 청소 (별도 cron 작업으로 후속)
  • non-git 환경 (본 proposal 은 git worktree 기반 워크플로우 전제)
  • 기존 .dev-kit/hand-off/linear/main.json 의 마이그레이션 (1회성 migration script 는 rollout 단계에서 별도 PR)
  • multi-team / multi-project 환경 (단일 Linear project 가정)

트레이드오프 (정직하게)

  1. false positive — investigation worktree 도 issue 생성됨 investigate/why-foo-fails 같은 브랜치도 Linear issue 가 생긴다. → 해결: branch pattern ^(investigate|research|spike)/ 은 tracking-only 모드로 강등 (issue body = "investigation, no implementation"). user 가 명시적으로 close 가능.
  1. scope 추출 실패 시 fallback — branch name 만으로 issue 제목을 만들면 noise (fix/typo → "Fix: typo"). branch 가 너무 generic 하면 user 에게 prompt 로 제목 받기. → 해결: _extract_scope() 가 branch verb (fix/feat/refactor/chore) + noun (slugified) 만으로 못 만들겠다 판단하면 (length < 3, 동사만 있음 등) hook 이 user prompt 로 제목 요구.
  1. 기존 사용자 워크플로우 breaking — PreToolUse autosync 에 의존하던 유저 (있다면) 는 즉시 중단. 마이그레이션 가이드 필요. → 해결: 1-release deprecation 경고 후 제거. release notes 에 명시.
  1. network failure 시 worktree cut 자체가 block — Linear API down 이면 작업 시작 못함. 15s timeout 으로 빠지지만 그래도 fail-closed. → 해결: LINEAR_REQUIRED=0 env 또는 per-repo config 로 bypass 가능 (warning 만 출력). default 는 fail-closed.

성공 지표

  • 중복 작업 0건 — 동일 scope 의 동시 worktree cut 시 1개만 생성되고 나머지는 link
  • 100% worktree 가 Linear issue 를 가짐 — .worktrees/<slug>/.dev-kit/linear.json 존재율
  • Edit-time hook 발화 0회 — PreToolUse linear 관련 hook 제거 후 tools/token_efficiency_analyzer.py 의 hook cost 가 감소
  • PR merge 시 state 자동 전이 100% — 기존 linear-pr-sync.yml 그대로
