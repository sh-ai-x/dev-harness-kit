Decision rule: accept issues, not PRs by default

This proposal deliberately refuses to equate “the issue is valid” with “the current PR should merge”. For each open item, apply this sequence:

  1. Accept or reject the observed problem independently of its proposed implementation.
  2. Identify the orchestrator boundary: state, edit gate, artifact, side effect, verification, recovery, measurement, or documentation.
  3. Keep the current PR only if it changes one boundary, has a narrow file set, is rebased on origin/main, and has green required checks.
  4. Otherwise mark the PR superseded/closed with a link to the accepted issue and create a replacement PR from origin/main.
  5. Do not close the issue until the replacement is merged and its boundary-level acceptance test passes.

This makes #838, #836, and #797 candidates for replacement rather than presumed merge candidates. #835 may merge independently because it is documentation-only, and #840 may be recreated as a small isolated fix after its conflict is resolved.

Cons, limitations, and accepted trade-offs

Trade-off A — minimal fix vs integrated refactor

A path-aware guard fix and a promotion command are less elegant than a unified orchestration abstraction, but they are observable and reversible. The proposal accepts temporary adapters and duplicate boundary code until traces show which abstraction is actually shared.

Trade-off B — explicit promotion vs automatic DONE promotion

Manual promotion leaves a short-lived operator step and is not the final unattended experience. It is chosen first because it avoids coupling lib/execute.py, cleanup, and artifact layout in one risky PR. Automatic promotion is accepted as O1.1 only after the command is idempotent and its failure behavior is visible in next_action/blockers.

Trade-off C — split PRs vs delivery speed

Closing/superseding #838, #836, or #797 can feel slower than merging a large bundle, but it reduces review ambiguity and makes rollback local. The proposal prefers two independently mergeable small PRs over one fast PR that couples cleanup, latency, and protection behavior.

Trade-off D — fail-closed vs unattended continuity

Ambiguous retention, missing evidence, or unverified staged content may stop a run. That is an intentional cost: a visible RECOVERY_REQUIRED state is preferable to deleting retained work, publishing conflict markers, or claiming independent verification that did not happen.

Trade-off E — measured optimization vs perceived speed

#837 and the narrowed #836 may not immediately remove every second of

tool overhead. Measurement is required first because an optimization that bypasses hook stages or increases false resumes can lower total harness effectiveness even if wall-clock time improves.

Acceptance gates and exit criteria

A replacement PR is ready for review only if it satisfies all applicable gates:

  • One issue, one boundary, one rollback path; no unrelated cleanup or documentation bundle.
  • Based on current origin/main; current PRs may be closed or marked superseded rather than repaired indefinitely.
  • Reproducer test exists for the incident or bottleneck being addressed.
  • Hook changes preserve fail-closed behavior and generated hook-matrix parity.
  • External side effects have dry-run/default-safe behavior and explicit provenance.
  • A completion claim includes command, exit code, check identity, and artifact path; an agent exit code is not independent verification.

O0 is complete when the #842 reproducer passes without disabling the guard. O1 is complete when a fresh session can promote and read a phase bundle after the runtime directory is unavailable. O2 is complete when force-push and staged-conflict reproductions are deterministic. O3 is complete when no cleanup candidate can be retained accidentally and the reduced hook/CI PRs have green required checks.

Only after O0–O3 should the project judge overall harness effectiveness with prevention, first-pass, recovery, measurement integrity, and learning components. Until independent evidence exists, report insufficient evidence rather than a synthetic score.

Before / After

Before (current state)

The previous triage treated the open PR list as a merge queue. That is the wrong abstraction for an orchestrator: an orchestrator is blocked by a few state-boundary failures, while many open PRs are optional improvements or risky bundles. A PR can be valuable without being mergeable, and an issue can be accepted without accepting its proposed implementation.

The actual execution path already has a state machine and durable fields. RalphState persists the stage, attended lock, next action, blockers, and per-stage state (skills/ralph/lib/ralph_state.py:100-123). The attended chain persists each sub-stage and lands in DONE, RECOVERY_REQUIRED, or USER_MERGE_REQUIRED (skills/ralph/lib/ralph_chain.py:347-366). The main bottleneck is therefore not a lack of another coordinator; it is the gap between those state transitions and the files, worktrees, hooks, and evidence that an interrupted session must safely use.

Four concrete boundary problems dominate the backlog:

  1. Hard stop: Issue #842 reports that worktree-guard reads ambient cwd for its main/worktree discriminator while a subagent's target is in a valid worktree. This denies normal Edit/Write and encourages unsafe Bash-write or guard-disable workarounds.
  2. Continuity/audit bottleneck: Issue #841 reports that phase artifacts live in gitignored runtime directories. A completed run can therefore be technically DONE but impossible for the next session or reviewer to reconstruct. The build contract also says the runner does not copy its long-running template bundle (skills/build/SKILL.md:161-183).
  3. Side-effect risk: PR #838 combines janitor, retention, cooldown, and advisory behavior. Its current checks are not green, and the described retention import/cwd failures make cleanup both non-reliable and potentially destructive.
  4. Truth/throughput gap: the executor records checks_run=[] and independent=false for its verify event (lib/execute.py:917-934), while PR #836 and Issue #837 target hook/tool latency. Optimizing before the orchestrator can prove what happened risks making an incorrect run faster rather than making it safer.

After (proposed state)

The backlog is reordered around the orchestrator's critical path rather than PR age or feature size. The first wave fixes the hard edit gate and creates a small, explicit artifact-promotion boundary. The second wave makes unattended side effects safe. Only then do we split and rework the large hygiene/latency/retry PRs.

The default disposition is now accept the problem, not necessarily the PR. A current PR is accepted only when it has one bounded responsibility, is based on current origin/main, has green required checks, and has a rollback that does not require disabling the orchestrator's protections. Otherwise the issue remains accepted, the PR is superseded or closed with a cross-link, and a smaller replacement PR is created.

The target architecture is intentionally layered:

  • State layer: RalphState owns transitions, attended locking, next action, and blockers.
  • Execution layer: lib/execute.py owns step lifecycle and subprocess evidence; it does not decide hook policy or cleanup policy.
  • Boundary adapters: a small promotion command, guard path resolver, and side-effect gates translate state into files or external actions.
  • Protection layer: worktree/TDD/pre-commit/destructive-confirm hooks remain fail-closed and independently testable.
  • Measurement layer: effectiveness reports consume provenance; they do not manufacture independent verification from an agent exit code.

Pros

  • Uses the orchestrator's actual state boundaries instead of adding another broad coordination layer.
  • Separates risk from bottleneck: #842 is an immediate stop-the-line fix, while #838 is treated as a high-risk side effect that must be split before use.
  • Allows the team to accept #841, #830, and #795 while rejecting or superseding their current PR shape when a smaller replacement is safer.
  • Makes the simplest viable solution explicit: a promotion command can establish durable evidence before automatic executor wiring is attempted.
  • Reduces blast radius, review ambiguity, and rollback cost by enforcing one issue, one boundary, and one focused PR.
  • Preserves the existing Ralph attended-lock state machine and keeps hooks, execution, cleanup, and metrics independently testable.

Cons

  • Replacing existing PRs creates short-term coordination work: issue/PR cross-links, supersession notes, and possible duplicate review.
  • The first #841 solution may require an explicit promotion call; automatic promotion on DONE is a follow-up unless the orchestrator integration is proven small and safe.
  • Splitting #838 delays the convenience of one hygiene bundle and may leave some cleanup features unavailable while the safety patch is reviewed.
  • A narrow #836 patch may leave some prompt advisories or context-window costs in place until a later measurement-driven change.
  • Strict evidence and fail-closed retention checks can make unattended runs stop more often at first; the trade is visible recovery instead of silent corruption or deletion.

Limitations

  • The priority scores are heuristic because the repository does not yet have a stable corpus for stop rate, recovery time, artifact-loss rate, or per-hook latency.
  • Path-aware worktree detection covers registered repository worktrees; external workspaces, unusual symlink layouts, and tool payloads without file_path remain separate contracts.
  • A promotion command can preserve the canonical evidence bundle, but cannot recover artifacts that were already deleted or logs that were never emitted.
  • This is a boundary refactor plan, not a full rewrite of lib/execute.py, RalphState, or the effectiveness schema. Those larger changes require measurements from the first wave.
  • The proposal cannot decide ownership, reviewer availability, or whether a failing remote check is infrastructure noise; those remain explicit merge gates.
