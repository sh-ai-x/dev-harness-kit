Executive summary

The user wants:

  1. Intermediate proposal approvals — not just ONE approval at the proposal HTML. Review surfaces at research, proposal, plan, and ship-confirm.
  1. Scope and ambiguity spelled out — the proposal enumerates in-scope, out-of-scope, and a numbered list of open questions so the reviewer can see the unknowns before approving.
  1. Iteration loop — at every gate the user can Approve, Edit-then-approve (Ralph rewinds + re-renders), or Abort (Ralph exits cleanly with state preserved).
  1. Unattended execution after final approval — once SHIP_CONFIRM_GATE exits Approve, Ralph locks attended_lock and runs build / babysit-pr / ship with NO further AskUserQuestion or interrupt, until terminal state (DONE / RECOVERY_REQUIRED / USER_MERGE_REQUIRED).
  1. Linear excluded — per the user's explicit request, Linear is OUT OF SCOPE for Ralph. It stays a separate opt-in skill (/dev-kit:linear) outside the Ralph chain.

This is the Ralph Wiggum pattern (Geoffrey Huntley, ghuntley.com/ralph) adapted to dev-harness-kit's existing 6-skill chain with multiple contract surfaces instead of one. Geoffrey's discipline — make the loop durable, make the contract explicit at the front, make the failure surface at the end — is preserved, with the addition that the contract is now multi-stage.

Net verdict: ADOPT. Seven new files, ~+450 lines net. Existing proposal renderer ships a backward-compatible additive schema bump.

Problem statement

The previous proposal had ONE approval gate at the proposal HTML and a hard stop at evidence-plan's Phase 2. That has three gaps the user identified:

GapSymptom
No intermediate reviewsOnce plan starts, the user can't intervene until phases/<name>/index.json is committed — i.e. the plan result is reviewable only AFTER it's a fact
Ambiguity buried in YAMLOpen questions are scattered across 12 sections; no stable id, no rendered 'Ambiguities' surface
Scope inferred, not enumerated'In scope' / 'out of scope' lives in the limitations list, not in a citable boundary block
Linear hard-wiredStage 5 of the chain is Linear — the user wants Linear OUT
No indefinite iterationEdit-then-approve re-renders once; the user can't drive multi-round negotiation

The cold-start templates (templates/init.sh, feature_list.json, progress.log.md, session_handoff.md) already implement Geoffrey Huntley's "resume from durable state" discipline — they are built but unused by any top-level orchestrator.

Iteration loop (Edit-then-approve)

At every interactive gate the user can:

  • Approve → state machine transitions to next gate (or to ATTENDED_RUN if GATE 4)
  • Edit-then-approve → Ralph parses the user's reply, identifies referenced ambiguities (A1=ok, A2=no), applies the edits, and rewinds to the matching render step. The state machine calls rewind_to(stage) which clears downstream state and re-renders only the affected layers.
  • Abort → Ralph exits with state preserved at .dev-kit/ralph/<session>.json. Re-invoking /dev-kit:ralph <idea> resumes from the last persisted stage.

The rewind step is bounded — rewind_to(stage) only re-renders the changed stage + downstream empties. Double- rewinds inside a single Edit-then-approve response are refused (rewind_to accepts one target only).

attended_lock (hard wall)

Once SHIP_CONFIRM_GATE exits Approve, lib/ralph_state.py sets attended_lock=True. From that point forward:

  • ralph_state.can_ask_question() returns False
  • The orchestrator's AskUserQuestion tool calls are rejected at the state-machine layer (NOT just by convention — by invariant)
  • test_ralph_skill.py::test_attended_lock_forbids_ask asserts the invariant
  • If a future PR adds a code path that fires Ask inside ATTENDED_RUN (e.g. a CI-update prompt), the lock blocks it. The state machine emits a last_blocked_ask field for forensic logging.

State machine (lib/ralph_state.py)

Pure, no subprocess. Five top-level states + 3 terminals:

# Gates (interactive — AskUserQuestion allowed)
RESEARCH_GATE     = "RESEARCH_GATE"     # Gate 1
PROPOSAL_GATE     = "PROPOSAL_GATE"     # Gate 2
PLAN_GATE         = "PLAN_GATE"         # Gate 3
SHIP_CONFIRM_GATE = "SHIP_CONFIRM_GATE" # Gate 4

# Locked execution (no Ask)
ATTENDED_RUN      = "ATTENDED_RUN"      # build → babysit → ship

# Terminal (success)
DONE              = "DONE"

# Terminal (blocked)
RECOVERY_REQUIRED    = "RECOVERY_REQUIRED"
USER_MERGE_REQUIRED  = "USER_MERGE_REQUIRED"

# Valid transitions
RESEARCH_GATE → PROPOSAL_GATE → PLAN_GATE → SHIP_CONFIRM_GATE
SHIP_CONFIRM_GATE → ATTENDED_RUN (on Approve; sets attended_lock)
any_gate → rewind_to(stage)  (on Edit-then-approve)
any → RECOVERY_REQUIRED | USER_MERGE_REQUIRED

Long-running templates wiring

At Phase 6 (build) the orchestrator runs the same copy pattern the skills/build/SKILL.md "Long-running session templates" section already documents:

mkdir -p .worktrees/<phase>-step<N>/templates
cp -u templates/init.sh templates/feature_list.json \
   templates/progress.log.md templates/session_handoff.md \
   templates/ralph_progress.md \

Ralph adds templates/ralph_progress.md — a per-run progress log complement to the cross-task progress.log.md. It tracks: gate transitions with reviewer signature, last action, next action, blockers, operator-readable one-liner. Each Skill() invocation appends one line. The reviewer signature is the SHA of the user's Approve / Edit reply — gives forensics for the attended_lock transition.

Ambiguities (open questions)

  1. A1default
    How many gates are enough? Proposal picks 4 (research / proposal / plan / ship-confirm). Could go to 5 (insert 'phase-decomposition review' between plan and ship-confirm) or down to 3 (drop ship-confirm; rely on proposal + plan).
    Default: 4 — research.md is short enough to be a gate; ship-confirm exists so the user sees 'build is about to start unattended, here's the headline' before the lock.

Pros

  • Honors the user's two-part ask: (a) intermediate proposal approvals — 4 review surfaces, not 1; (b) once final approval is given, NO further Ask / interrupt until DONE / RECOVERY_REQUIRED / USER_MERGE_REQUIRED.
  • Each gate has a re-renderable artifact (research.md → main.html → PRD.md → ship-confirm.html). The user can iterate per-artifact instead of touching the YAML directly.
  • Edit-then-approve rewinds Ralph to the matching render step (rewind_to(RESEARCH_GATE) after a proposal edit, etc.) — the user never has to re-author the upstream YAML by hand.
  • Explicit ambiguity: enumeration forces the proposal author to name unknowns upfront. The renderer prints them with stable ids so reviewers can answer A2 = no, it's standard pytest parametrize in the Edit reply.
  • Explicit scope.in_scope: / scope.out_of_scope: lines turn the implicit 'don't change unrelated code' norm into a citable boundary. Reviewers can flag drift before it ships.
  • gate_contract: table documents each gate's input artifact + the question + the Approve/Edit/Abort semantics + which rewind each Answer triggers. Ralph and the user share the same surface; no hidden state.
  • attended_lock in ralph_state.py is the hard wall: after SHIP_CONFIRM_GATE exits Approve, the state machine rejects any AskUserQuestion invocation. Tested in test_ralph_skill.py::test_attended_lock_forbids_ask — invariant, not convention.
  • Honors MUST-NO-SKIP from babysit-pr: NEVER skips review, NEVER auto-merges, NEVER force-pushes to main. The final gh pr merge is the human-merge boundary — Ralph stops at 'PR green and approved'.
  • Honors MUST-36/37/38 (per-step sub-agent, 3-cycle self-fix, per-step worktree isolation) — Ralph never bypasses the per-step harness runner in lib/execute.py.
  • Linear is OUT OF SCOPE — Ralph does not create / sync / archive Linear issues. Per the user's request, Linear stays a separate opt-in. Removes 1 stage, 1 side-effect, 1 silent-skip path.

Cons

  • 4 gates = 4 review surfaces. The user must read 4 artifacts (research.md, proposal HTML, PRD.md, ship-confirm summary) before build runs. Mitigation: research.md is ≤ 1 page; ship-confirm is a 10-line summary; only proposal HTML and PRD.md are full-doc reads.
  • Edit-then-approve rewinds upstream artifacts. If the user edits the proposal AND then edits the PRD, Ralph re-renders both — 2 re-render cycles. Mitigation: the rewind step is bounded (rewind_to(stage) only re-renders the changed stage + downstream empties); the state machine refuses double-rewinds inside a single Edit-then-approve response.
  • ambiguity / scope / gate_contract fields require a renderer schema bump in skills/proposal/SKILL.md and lib/render_proposal_html.py. Existing proposals without these fields render unchanged (default to empty sections). Mitigation: backward-compatible — old proposals skip the new sections silently.
  • attended_lock is a new invariant. If a future PR adds a code path that fires Ask inside ATTENDED_RUN (e.g. a CI-update prompt), the lock will block it — debug surface is the state machine's last_blocked_ask field. Mitigation: test_attended_lock_forbids_ask + a debug-log emit when the lock fires.
  • Build's --skip-blocked escape is still off by default. Blocked steps halt Ralph. Mitigation: surfaced via ralph_progress.md; the operator resumes from the durable state checkpoint.
  • Skipping Linear entirely removes the auto-sync / auto-archive features that some users rely on. Mitigation: explicit Out-of-scope line in this proposal; if a future PR wants Linear back, it lands as a separate proposal under accepted/, not as a Ralph amendment.

Limitations

  • Cannot replace user judgement at any gate. Each HTML/YAML artifact is reviewed by the human; if the human approves a wrong design at gate 1, all downstream gates inherit the error. This is by design — the gates ARE the contract — but Ralph's correctness ceiling is the human's review quality.
  • Cannot detect silent doom loops inside a single build step (3 same Bash calls). build's MUST-37 self-fix + the 3-cycle no-progress guard catch most patterns. Ralph inherits the gap; it does not close it.
  • Cannot run without an active Claude Code session. When the session ends mid-chain, Ralph pauses at the last durable checkpoint. The next session resumes from templates/session_handoff.md — ~30-60s cold-start per session re-open.
  • Cannot bypass the 'human merges PR' boundary. Even after all 4 gates approve, the final gh pr merge is a human action — Ralph stops at 'PR is green and approved', not 'PR is merged'. This is MUST-NO-SKIP, not a Ralph limitation, but it is the hard wall on full autonomy.
  • Cannot re-propose mid-chain during ATTENDED_RUN. If build's 3-cycle guard or babysit-pr's MAX_ITERS surfaces RECOVERY_REQUIRED, Ralph exits; the user resumes via ralph resume (rewinds to SHIP_CONFIRM_GATE if state allows, else exits with the failure summary).
  • Cannot operate across repos. The chain is per-repo; multi-repo changes require a separate Ralph run per repo.
  • Cannot auto-answer the ambiguities in the Elicit-style ambiguity: block. The user must answer them manually (Edit-then-approve reply) or accept the proposal's default (Open question — answered by plan in --best-effort mode).
  • Cannot guarantee byte-identical re-runs. Ralph's orchestrator is deterministic (the state machine is pure), but the underlying skills (research citations, build sub-agent outputs, babysit-pr poll timing) are not. --dry-run is the only stable mode for the cold sub-agent test.
